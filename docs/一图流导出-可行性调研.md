> 落笔 2026-11-12。相关文档：[`开发说明.md`](../开发说明.md) §9.2（配队与计算）、
> [`docs/配队功能方案-草案.md`](./配队功能方案-草案.md)、[`web/js/team.js`](../web/js/team.js) 分享段。

## 实施记录（2026-11-12）

功能已落地，与本文初稿的偏差如下（以代码为准）：

| 项 | 初稿 | 实际 |
| --- | --- | --- |
| 顶部统计条 | 场上 / 精锐 / 总售价 / 已激活 / 已强化 / 待激活 六个统计块 | **整块去掉**（用户要求），改为**盟约图标带**：已强化（琥珀实线）/ 已激活（绿实线）/ 可激活（灰虚线 + 压暗），图标下标人数/门槛与层数 |
| 叠层统计 | 按词条聚合全部盟约 | **只统计已激活盟约**（用户要求）：未点亮的不生效，不计入；无激活盟约时显示空态 |
| 输出尺寸 | 1080 逻辑宽 × 2 倍 | 逻辑 1080，按 `min(2x, 面积 ≤6.5M, 单边 ≤7000)` 自动降采样 → 实测 1620×3233，PNG ≈1.1 MB |
| 首屏预算 | 120 → 132 KB | 120 → **145 KB**（qr.js 5.4 + poster.js 11.4 gzip；实测 140.2），已注明「下一档必须按需加载」 |
| 二维码校验 | 用 segno 生成黄金样本 | 改用 **python-qrcode**：segno 会在终止符后多补一个 `0x00` 再开始 `EC/11` 填充，逐位比对对不上（扫描不受影响，但不是标准填充序列） |
| 新增文件 | `js/qr.js` / `js/poster.js` | 同；两者都平铺在 `web/js/`，`build_dist.py` 的 basename 内联问题顺手修掉 |
| 出图流程 | 单遍绘制 | 先算「绘制指令列表」（`layout`）再一次性 `paint`，高度边排边加，不做两遍渲染 |
| 配色 | 读 CSS 变量 | 同；另加 `--cov-active/empowered/idle` 三组状态色在图上复用，主题一改即跟随 |
| 文案密度 | 未定义 | 用户要求精简：去掉生成时间、长脚注、「（含装备 / 层数）」；标题改 `GSPA 配队` + 赛季名，不标玩家填的层数 |
| 二维码视觉 | 白底黑码方块 | 收进圆角面板；圆角浅色卡片 + 微圆角实心模块 + 圆角定位眼（保持深码浅底、4 模块静区） |

验证方式：`test_qr`（15 项，含与 python-qrcode 的逐模块比对）、`test_poster`（17 项快照）、`smoke_team`（58 项，含面板与链接往返）、headless Edge 实拍五种场景，并把生成的 PNG 用 Python 从像素反读二维码（45×45 全部一致，静区干净）。

## 0. 一句话结论

**可以，而且不需要后端、不需要改数据表、不需要新依赖服务。**
一图流里的六块内容（配队码 / 干员头像+名字 / 激活盟约 / 叠层统计 / 二维码 / 码文）里，
**五块的数据现在都已经在内存里算好了**，缺的只有两件事：

1. **二维码编码器**（本项目零外部请求、零 CDN，不能用在线 QR 接口）；
2. **把数据画成一张 PNG 的渲染器**（现在没有任何 canvas / 截图代码）。

真正的工作量不在算法，在**版式打磨**和**二维码/画布那几个平台坑**（`file://` 画布污染、
单文件版无头像、localhost 链接不可扫、首屏 gzip 预算只剩 1.5 KB）。

预估 **2–3 个工作日**（R1 数据与二维码 1 天 → R2 画布版式 1.5 天 → R3 入口与验收 0.5 天）。

## 1. 需求拆解与现状核对

| 一图流需要的内容 | 现在有没有 | 现成来源 | 缺口 |
| --- | --- | --- | --- |
| **配队码** `GSPA3.xxxx` | ✅ 有 | `web/js/code.js` `Code.encode(team, data)`；8 人满编约 22–24 字符 | 无 |
| **干员头像 + 名字** | ✅ 有 | `data.operators[].avatar/avatarFull`（96 / 180px WebP）；`UI.avatarHtml()` 已做「缺图回退色块首字」 | 画到 canvas 要先把 `<img>` 解码好（异步），不能用 DOM 片段 |
| **精锐 / 自选 / 阶数 / 售价** | ✅ 有 | `Calc.evaluate()` 的 `pieces[]`（`op`、`elite`、`pick`、`items`）+ `summary` | 无 |
| **激活盟约信息** | ✅ 有 | `Calc.evaluate().rows[]`：`state`（`empowered/active/near/inactive/conflict`）、`count`、`threshold`、`bonus`（调和 +1）、`layer`、`node`、`nodes` | 无 |
| **盟约数值随层数换算** | ✅ 有 | `Calc.substLayers(valueText, layer)`、`Calc.layerSegments()` | 无 |
| **叠层统计（每回合上限）** | ✅ 有（**但是私有函数**） | `team.js` 的 `traitGroups(team).capsByBond` → `[{bond,total,parts:[{name,amount}]}]`，已在词条栏渲染成 `+N（a+b）` | 需要导出成公开 API（见 §5） |
| **二维码** | ❌ 没有 | — | 需内置一个纯 JS QR 编码器（约 3–4 KB gzip） |
| **一张图片文件** | ❌ 没有 | 全站没有 `<canvas>`、没有 `toBlob`、没有 html2canvas | 需写 Canvas 渲染器 |
| **链接直达** | ✅ 有 | `#/team?c=GSPA3.xxx`，`store.js` L244–248 中 `c=` 的优先级最高，打开即还原整队 | 二维码里放的就是它；但**当前地址在 localhost / file:// 时不可扫**，需要有线上地址兜底 |
| **图片保存 / 转发** | ❌ 没有 | 现在只复制文本 | `toBlob` + `<a download>` + 预览面板长按保存 |

结论：**这是纯增量功能**，`test_calc.mjs` / `test_code.mjs` 覆盖的判定与编码逻辑一行都不用动。

固定宽度 **1080 px**（高度随内容自适应，约 1500–1900），2 倍绘制（2160 宽）再缩到 1080 输出，

## 3. 渲染路线选择

| 方案 | 做法 | 优点 | 致命问题 |
| --- | --- | --- | --- |
| **A. Canvas 2D 手绘**（推荐） | 全部用 `fillRect / drawImage / fillText` 画；头像与图标预加载成 `HTMLImageElement` 后 `drawImage` | 零依赖、体积可控、可精确控制像素对齐、同源图片不污染画布、离线可用 | 文本换行、圆角、虚线要自己写（约 150 行工具函数） |
| B. HTML → SVG `foreignObject` → `img` → Canvas | 复用现有 `.cov` / `.slot` 的 DOM 与 CSS | 版式改 CSS 即可 | 必须把整份 `app.css` 内联进 SVG、图片要转 data URI；`file://` 下取不到 CSS 文本；Chrome 对 foreignObject 里的字体/外链资源限制多，坑比写字多 |
| C. 引 html2canvas / dom-to-image | 第三方库截 DOM | 上手快 | 违背「零外部请求 / 单文件可拖拽」；~45 KB 起，gzip 也不小；本地 webp 仍需 CORS 处理 |
| D. 后端 / CI 出图 | 服务端渲染 | 图最漂亮 | 本项目**没有任何后端**，部署是纯静态 Pages；为一张图引服务不值得 |

**选 A。** 理由不只是「轻」：一图流的版式是**数据驱动的固定版式**，不是「把页面截下来」。
用 canvas 画，等于把版式写成一个纯函数 `draw(model) → canvas`，可以：
- 单测里用假 ctx 断言「画了哪些文字/图片、顺序对不对」（§9）；
- 以后加「浅色版 / 透明底 / 1080×1920 竖图」只是换参数。

## 4. 二维码方案

### 4.1 扫出来打开什么

现行分享链接已经是这个形态（`team.js` L1091–1100）：

```
https://haixingjun.github.io/GSPA-Glasses-Stronghold-Protocol-Assistant/#/team?c=GSPA3.<code>
```

- `store.js` `parseHash()` 里 `c=` **优先级最高**，打开就还原整队（含装备、转职、层数、自选）；
- 比 `t=&e=&it=&m=&p=&L=` 那种长参数短一半以上，二维码能小一档；
- 长度实测估算：域名+路径 72 + `#/team?c=` 9 + 码 24 ≈ **105 字节**（带 2 件装备约 110）。

### 4.2 版本与尺寸测算（byte 模式）

| EC 级 | 105 字节落在哪个版本 | 模块数 | 4 模块静区后总格 | 5px/模块 | 6px/模块 |
| --- | --- | --- | --- | --- | --- |
| L | V5（容量 106，仅 1 字节余量） | 37×37 | 45 | 225px | 270px |
| **M** | V6（容量 106，同样只差 1 字节）→ **实际会升到 V7（122）** | 45×45 | 53 | 265px | **318px** |

建议 **EC M + 自动选版本（V1–V10）**，绘制时 `module = 6px`、**整数像素对齐**，输出约 318×318，
贴在一图流右下角。理由：M 能容忍约 15% 污损（微信压缩、截图裁边）；码长会随装备增加，
必须「按实际码长自动选版本」，不能写死 V6。

> 域名叫得短一点（自定义域名）还能降到 V4，但这不是本轮的事，留 `window.GSPA_SITE` 覆盖口子即可。

### 4.3 编码器实现范围（自写，约 400–500 行）

只做**这个站点需要的子集**，不做通用库：

- 模式：**byte（8-bit）only**——URL 里没有 QR 数字/字母模式能省的那点空间，不值得多写两套状态机；
- 版本：V1–V10 自动选最小可容纳版本；EC 级固定 **M**；
- 内容：Reed–Solomon 纠错（GF(256)）、交织、8 种 mask 的罚分选优；
- 输出：`{size, modules: Uint8Array(size*size)}`，由渲染器负责画矩形。

体积预估：**~8–10 KB raw / ~3–4 KB gzip**（含版本容量表、对齐图形位置表、RS 表）。
**必须遵守 ES5 语法**（与 `team.js` / `calc.js` 一致，老 WebView 不能白屏）。

### 4.4 一致性自检（重要）

出图前做一次闭环：

```js
const text = Code.encode(team, data);
const back = Code.decode(text, data);        // 已经是纯函数
if (!back || !sameTeam(back.team, team)) → 不画二维码，toast「码生成异常」
```

这样即使以后改 `code.js` 的位流布局，也不会发出一张**扫出来是别的队**的图。
`sameTeam` 只比 `slots`（k/p/e/it/m）与 `layers`，20 行足够。

### 4.5 二维码怎么测

自研编码器最大的风险是「画得挺像，扫不出来」。三层验证：

1. **结构单测**（`tools/test_qr.mjs`，Node，零依赖）：finder/timing/alignment 图形位置、
   format info 的 BCH 位、惩罚分选出唯一 mask、同一输入两次输出一致；
2. **黄金样本**：用 `pip install segno`（仅开发机、仅生成测试数据，**不进运行时、不进构建**）
   对 5 组固定字符串（含本项目的真实 URL）生成模块矩阵，存成 `tools/fixtures/qr-*.json`，
   单测逐模块比对——这是唯一能证明「编码正确」的办法；
3. **真机扫**：headless Edge 出图后用手机相机 / 微信扫；再在 Chrome 里用 `BarcodeDetector`
   （有就测，没有就跳过）做一次程序化回读。

## 5. 叠层与盟约数据：复用，不要抄第二份

`team.js` 里算叠层上限的链路是（L405–656）：
`isLayerTrait` → `parseTraitCaps` → `traitLayerCaps`（含「通用词条按已激活盟约分摊」）→ `mergeCap` → `capRowsOf`。
这段是**配队页和图片唯一的口径**，绝不能在一图流里重写一遍——否则页面显示 `+6`、图上写 `+5`。

做法：在 `team.js` 末尾把 `traitGroups` 暴露出去，并提供**一个纯数据快照函数**（不碰 DOM、可在 Node 里跑）：

```js
// team.js 新增
function posterModel(team) {
  var res = Calc.evaluate(team, data);
  var bag = traitGroups(team);
  return {
    version: data.version,              // data.json 顶层字段
    summary: res.summary,                 // filled/size/elite/price/picks/active/total
    pieces: res.pieces.map(function (p) { // 席位（顺序即场上顺序）
      return { name: p.op.name, avatar: p.op.avatarFull || p.op.avatar,
               tier: p.op.tier, tierLabel: p.op.tierLabel, price: p.op.price,
               elite: p.elite, pick: !!p.pick, tags: p.op.tags || [],
               items: p.items.map(function (it) { return { name: it.item.name,
                                                           icon: it.item.iconFull || it.item.icon,
                                                           elite: it.elite }; }),
               morph: p.morph ? p.morph.covenant : '' };
    }),
    covenants: res.rows.filter(function (r) {     // 已激活 / 已强化
      return r.state === 'active' || r.state === 'empowered';
    }).map(function (r) {
      return { name: r.name, rank: r.rank, state: r.state, kind: r.kind,
               count: r.count, threshold: r.threshold, bonus: r.bonus,
               layer: r.layer, node: r.node, nodes: r.nodes,
               empower: r.empowerThreshold, missingEmpower: r.missingEmpower,
               value: r.layer ? Calc.substLayers(covByName[r.name].valueText, r.layer) : '' };
    }),
    near: res.rows.filter(function (r) { return r.state === 'near'; })
                  .map(function (r) { return r.name; }),
    caps: bag.capsByBond,                 // [{bond,total,parts:[{name,amount}]}]
    picks: res.summary.picks, pickLimit: res.summary.pickLimit
  };
}
```

公开：`Team.posterModel(team)`。**渲染器只吃这个对象**，不再碰 `Store` / `data` / DOM。
好处：`test_poster.mjs` 能直接断言「炎 6/3、+6（2+2+2）、cap 排序」，不需要 DOM 桩和 canvas。

## 6. 渲染管线（一次点击发生了什么）

```
点「一图流」
  → ① model = Team.posterModel(Store.getTeam())        // 同源口径
  → ② code  = Code.encode(team, data) + 自检回解         // §4.4
  → ③ url   = pickLinkBase() + '#/team?c=' + code       // §7.3 地址兜底
  → ④ qr    = Qr.encode(url)                            // 纯计算
  → ⑤ loadImages([头像… 图标… qr不需要])                 // 并发，单个 1.5s 超时
       任何一张失败 → 该格画「色块 + 首字」回退，不阻断出图
  → ⑥ canvas = drawPoster(model, qr, images, theme)      // 纯函数，返回 canvas
  → ⑦ canvas.toBlob('image/png') → 预览面板（<img src=blobURL>）
  → ⑧ 面板按钮：下载 PNG / 复制图片（Chrome）/ 复制分享文本 / 长按保存提示
```

关键点：

- **首帧不碰 canvas**：模块加载时只注册函数；`document.createElement('canvas')` 只在 ⑥ 里出现，
  否则 `smoke_team.mjs` 的 DOM 桩（没有 canvas）会直接崩。
- **图片解码**：`img.onload/onerror` + `setTimeout` 兜底；同一 URL 去重（8 人都带同一件装备时只下一次）。
- **画布污染**：`file://` 下 webp 会让 canvas 变 tainted，`toBlob` 抛 `SecurityError`。
  检测 `location.protocol === 'file:'` 时**不加载图片**，直接用首字色块画（图会朴素但一定能出）。
- **输出尺寸**：2× 绘制 = 2160 × ~3800 ≈ 8.2 M 像素，低于 iOS Safari 的 16.7 M 上限；
  若内容超长（很多盟约 + 长词条），改为 1.5× 绘制兜底。
- **字体**：`ctx.font = '600 40px ' + getComputedStyle(document.documentElement).getPropertyValue('--font')`
  —— 系统字体，与页面一致，不需要内嵌字体。

## 7. 已知坑（每一条都要在实现里落地）

| # | 坑 | 影响 | 对策 |
| --- | --- | --- | --- |
| 7.1 | **单文件版没有头像/图标**（`GSPA_NO_AVATARS` / `GSPA_NO_ICONS`） | 最常被转发的恰恰是 `standalone.html`，图里全是色块 | 渲染器接受 `NO_AVATARS` 并画「色块+首字+盟约名」；面板上给一句「单文件版不含头像，想要带图的一图流请用在线版」 |
| 7.2 | **`file://` 画布污染** | 双击打开时导出必定报错 | 见 §6 的 `file:` 分支；面板文案改成「当前是本地打开，图内不含头像」 |
| 7.3 | **localhost 链接不可扫** | 本地预览出的二维码，别人扫开是 127.0.0.1 | `pickLinkBase()`：`http(s)` 且 **不是** `localhost/127.0.0.1/192.168.*/10.*` 时用当前 origin；否则用常量 `SITE_FALLBACK = 'https://haixingjun.github.io/GSPA-Glasses-Stronghold-Protocol-Assistant/'`；再留 `window.GSPA_SITE` 覆盖 |
| 7.4 | **`build_dist.py` 内联按 basename 查表** | 新脚本若放在 `js/vendor/qr.js`，单文件版会内联成**空文件**（`js_src.get(src.split('/')[-1])`） | 新文件**平铺**在 `web/js/`（`qr.js` / `poster.js`），或者顺手把 `inline_script` 改成按完整相对路径取 |
| 7.5 | **`smoke_team.mjs` 里脚本列表是硬编码的** | 加了模块不更新，冒烟测试就覆盖不到，甚至因为全局对象缺失挂掉 | 同步 `scripts` 数组；新模块加载时不得触碰 canvas |
| 7.6 | **首屏 gzip 只剩 1.5 KB** | 当前 118.5 / 120 KB（`dist/BUILD_INFO.txt`）；QR + 渲染器约 +8–10 KB | 二选一：①把 `BUDGET_KB` 上调到 **132**，在构建报告与文档里写明理由（推荐，简单）；②`poster.js` 按需动态加载（目录版单独 chunk），`build_dist.py` 额外把它内联成 `<script type="text/plain">` 由 loader `eval`（能把首屏压住，但多 20 行构建魔法） |
| 7.7 | **iOS / 微信不能"下载"** | 点了下载没反应 | 面板主按钮是「长按图片保存」+ 「下载 PNG」并存；桌面端直接 `a[download]`，`navigator.share({files})` 可用时优先系统分享 |
| 7.8 | **深色/浅色与压缩** | 深色底图被微信压得一坨黑 | 提供「深色 / 浅色」二选一，默认跟随当前主题；正文最小字号 ≥22px@1080 |
| 7.9 | **叠层上限是启发式** | 图上写错数字比不写更糟 | 区块标题固定为「叠层上限（按词条估算）」，脚注写「仅统计词条里明示的每回合上限，未计队友加成」；页面上已有同样口径，保持一致 |
| 7.10 | 头像清晰度 | 96px 头像画到 176px 会糊 | 一图流统一用 `avatarFull`（180px），88px 显示 @2x = 176px 刚好 |
| 7.11 | 自选干员没有词条 | 图上叠层统计会缺 | 与页面一致：脚注「另有 N 名自选干员暂无词条数据」 |

## 10. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 自研 QR 编错 | 图看着正常但扫不出来，用户不会反馈原因 | 三层验证（§4.5）；宁可**先显示码文、二维码画不出来就不画**，绝不画一张错码 |
| 画布版式返工 | 一图流的"好看"是主观的，容易改到第 6 版 | R2 第一版先 4 行骨架（无头像、无圆角）定信息层级，再叠视觉；版式参数集中成一个 `LAYOUT` 常量对象 |
| `file://` / 单文件版的图不好看 | 最常被转发的形态恰恰没图 | 面板上明示「在线版可带头像」；或 P3 再考虑把 180px 头像做成可选内联包（会让单文件版从 538 KB 涨到 ~4 MB，不建议） |
| 叠层口径被当权威 | 图片会脱离上下文传播 | 区块标题与脚注都写明「估算 / 仅按词条」，并在右下角固定水印「非官方 · 以游戏内为准」 |
| 预算上调被质疑 | 每次加功能都上调，预算形同虚设 | 一次性写入 `开发说明.md`：132 KB 的组成（QR 4 + 渲染器 6）与"下一档必须拆包"的红线 |
| 版权 | 头像来自 PRTS（CC BY-NC-SA），出图等于把素材二次分发 | 图上保留「非官方 / 素材来自 PRTS」脚注；与 NOTICE.md 的非商业口径一致；不做付费/商用场景 |

## 11. 需要拍板的 5 个问题

1. **出图入口**：放「分享」面板里（分享 = 文本 + 图片二选一），还是顶栏同级放一个独立的「一图流」按钮？（推荐后者：分享是"发文字"，出图是"发图"，心智不同）
2. **图里要不要放"未激活/待激活"**：只放已激活（图短、干净）还是也把"缺 N 人"列出来（信息全、图长）？推荐：已激活全列 + 待激活压成一行。
3. **叠层统计的粒度**：只放「每盟约上限 + 总数」（1 行/盟约），还是连「哪位干员贡献了几层」都写进图里？（后者信息量大但图会明显变长）
4. **二维码指向**：固定线上地址（`haixingjun.github.io`，谁来部署都能扫），还是跟随当前域名（自定义域名时更短）？推荐：跟随，但 localhost/内网/`file:` 回退到固定地址。
5. **预算**：接受把首屏 gzip 预算从 120 提到 132 KB（简单路径），还是要求按需加载把首屏压在 120 以内（多一套加载器，构建变复杂）？

## 附：为什么不做成"长图分享到图鉴页"

有人会想要"任意视图都能一键截图"。本轮**不做**：
- 图鉴页是无限列表，截图天然是"当前可视区"，价值远低于一张信息密度固定的配队图；
- 一图流的价值在于**结构化**（谁、几个盟约、多少层、怎么复现），而不是"把页面拍下来"。
- 真要做，`drawPoster` 之外还要一套"通用 DOM 快照"，那是另一个 3 天。
