> [`卫戍协议·规程/PRTS盟约记录`](https://prts.wiki/w/卫戍协议·规程/PRTS盟约记录)（26 条盟约成员表）

## 1. 结论

| 问题 | 现在能不能答 | 依据 / 缺口 |
| --- | --- | --- |
| 「斩业星熊」是不是真实干员？ | **能** | PRTS 有独立页；`charId=char_1044_hsgma2`；热更资源含 `avg_1044_hsgma2_1.ab` |
| 她是否在本期固定干员名单（143 条）里？ | **能，且是否** | `source/卫戍协议_完整数据表.xlsx` 的「干员与特质」只有 143 名具名 + 12 条自选配置，没有星熊 |
| 她能不能进「自选配置」槽？ | **能** | 6★、非固定干员；符合 PRTS 的「甄选」条件（自身持有 6★、不可选固定干员） |
| 她会归到哪个盟约？ | **能推，炎** | PRTS `ingameFaction=炎-龙门,龙门近卫局`；`炎-龙门 → 炎`；隐藏阵营「东」不产生核心盟约 |
| 这个能力可不可做？ | **可做** | 数据源（PRTS Cargo）已能批量给出 `charId / 稀有度 / 阵营 / 隐藏阵营`；固定名单可做回归校验 |
| 有没有数据缺口？ | **有一个软缺口** | 本地 `source/` 只是本期卫戍汇总，**不含全量干员表**；要严格校验「解包出现」需补一份 slim 的官方 `character_table` 索引，或接受 PRTS `charId` 作为解包代理 |

## 2. 官方机制（PRTS 原文）

PRTS 的 [`卫戍协议`](https://prts.wiki/w/卫戍协议) 在「物资的调配 → 干员」一节写明：

> 除了固定参与的模拟干员，第Ⅴ阶和第Ⅵ阶中各自存在 2 个“甄选”槽位，玩家可以选择**自身持有的 6★ 干员**加入本次模拟作战。
> * **不可甄选加入已在名单中的固定干员。**
> * 前述的罗德岛特派高级资深干员也将加入可甄选阵容供玩家选用。
>
> 甄选加入的干员会**根据其实际阵营所属分配核心盟约**，若没有可匹配的则改为分配**协防干员**盟约。
>
> 原型干员会继承其补位干员的特质，但**甄选加入的干员不会拥有任何特质**。

由此得到四条硬规则：

1. **准入**：6★ + 自身持有 + 不在固定名单。
2. **盟约**：只按阵营分配**核心盟约**；无匹配 → **协防干员**。
3. **特质**：无（普通/精锐都不显示特质）。
4. **槽位**：PRTS 写的是每阶 2 个；本仓库主表是 5 阶/6 阶各 6 条（见 §3），**以数据驱动、不要硬编码 2**。

## 3. 数据盘点：三份数据各自能回答什么

| 来源 | 有什么 | 能回答 | 不能回答 |
| --- | --- | --- | --- |
| 本地 `source/卫戍协议_完整数据表.xlsx` | 8 张表；干员与特质（143 具名 + 12 自选配置）、盟约、装备道具、策略、原始参数 2,720 行 | 本期固定名单、固定干员的盟约/特质/售价 | 全量干员是否存在、6★ 稀有度、阵营、任意干员的 `charId` |
| 主表 `卫戍协议数据表.xlsx` | 7 张表，干员表 155 行（含 12 条 `自选配置`，`盟约一~三` 为空） | 配队/图鉴的既有口径 | 同上 |
| PRTS Cargo（`chara` + `chara_data`） | `_pageName`、`charId`、`charIndex`、`rarity`、`profession`、`subProfession`、`nation`、`org`、`ingameFaction`、`hiddenFaction` | 6★ 名单、`charId`（解包 ID）、阵营、隐藏阵营、职业/分支 | 玩家是否真的持有；赛季专属的「甄选」实测口径 |
| 官方 `character_table.json`（可选补入） | 全量干员的 `charId / name / rarity / nationId` | 严格的「解包存在」校验 | 需要新增一份 slim 索引，约 100 KB；本地 `source/` 目前没有 |

### 3.1 一个已确认的细节：自选配置是「占位行」

主表 155 行里有 12 条：

```text
自选配置 5阶-1 … 5阶-6   tier=V  price=4  tags=[]  normalText=按自选干员配置
自选配置 6阶-1 … 6阶-6   tier=VI price=4  tags=[]  normalText=按自选干员配置
```

它们不是真实干员，而是「甄选槽位」的占位；当前配队候选池明确排除了它们：

- `web/js/team.js` L757：`if (op.type === '自选配置') continue;`
- `开发说明.md` L604：「自选配置 12 行不参与配队（无盟约标签），候选池已排除。」

这正是本功能要补的口子：**给占位行一个「实际干员 + 阵营推导出的盟约」，让它参与计数。**

> 槽位数不一致：PRTS 说每阶 2 个，主表是每阶 6 条。两种可能：本期规程实际更多，或主表把「槽位 × V/VI」拆成了 6 组。建议保持数据驱动，另加一个「游戏上限」提示（默认 2/阶，可配置），不要在主表里改行数。

## 4. 样例逐项核对：斩业星熊

### 4.1 PRTS 侧

用 Cargo 查 `chara` + `chara_data`（实际返回）：

```json
{
  "name": "斩业星熊",
  "charIndex": "383",
  "charId": "char_1044_hsgma2",
  "profession": "重装",
  "subProfession": "驭法铁卫",
  "rarity": "5",
  "nation": "炎-龙门",
  "ingameFaction": "炎-龙门,龙门近卫局",
  "hiddenFaction": "东"
}
```

- `rarity=5` 是 PRTS 的 0 基稀有度，即 **6★**。
- `ingameFaction` 是「游戏属性阵营」，第一段 `炎-龙门`；`-` 前是核心盟约「炎」。
- `hiddenFaction=东` 不匹配 10 个核心盟约，不产生额外核心标签。
- 结论：**核心盟约 = 炎**。

### 4.2 解包 / 固定名单侧

- `grep 星熊` 全仓库无命中；`source/卫戍协议_完整数据表.xlsx` 的「干员与特质」没有她；`web/data/data.json` 的 155 条里也没有她。
- 因此：**不在固定名单 → 可作为甄选候选**；同时说明本地「卫戍汇总」不能证明任意干员存在。
- 她的 `charId=char_1044_hsgma2` 来自官方数据；热更包资源列表里也有 `avg/characters/avg_1044_hsgma2_1.ab`，可佐证「游戏里确实有这名干员」。若要把「解包出现」做成硬校验，建议补一份官方 `character_table` 的 slim 索引（见 §7.2）。

### 4.3 归类结果

| 项目 | 值 | 说明 |
| --- | --- | --- |
| 固定干员 | 否 | 143 条里没有 |
| PRTS | 有 | 页面 `斩业星熊`，`char_1044_hsgma2` |
| 稀有度 | 6★ | `rarity=5` |
| 阵营 | 炎-龙门 / 龙门近卫局 | `ingameFaction` |
| 隐藏阵营 | 东 | 不产生核心盟约 |
| 核心盟约 | **炎** | `炎-龙门` 前缀映射 |
| 附加盟约 | 无（按原文推断） | 甄选只分配核心/协防；待实测 |
| 特质 | 无 | 原文明确 |
| 槽位 | 自选配置 5阶/6阶 任一 | 由槽位决定 V/VI；售价 4 |
| 结论 | **可甄选，计 1 名「炎」** | 炎 3 人激活、6 人强化 |

## 5. 盟约归类规则与证据

### 5.1 规则

> **2026-11-14 修正**：以下并集规则是调研阶段的旧口径，已不再用于自选干员。现行口径见
> [`自选干员阵营审计-2026-11-14.md`](自选干员阵营审计-2026-11-14.md)：
> `mainPower` 最具体阵营（team > group > nation）+ 全部 `subPower` → 核心盟约 `powerIdList` 求交，空 → 协防干员。
> 例：焰影苇草 `mainPower = victoria / tara` → 取 **塔拉** → 协防干员；煌 `mainPower = rhodes / elite`，
> `subPower = yan / victoria` → **炎 / 维多利亚**。

```text
（旧口径，仅作历史记录）
输入：ingameFaction（游戏属性阵营）+ hiddenFaction（游戏属性隐藏阵营）
1. 按 [,，;；] 切分（hiddenFaction 里出现过 "炎;;维多利亚"，双分号也要切）
2. 逐段归一：
   - "炎" / "炎-龙门" / "炎-岁" → "炎"（只对「炎」做前缀特判，避免 "乌萨斯学生自治团" 被误判）
   - 其余段与 10 个核心盟约名精确匹配（维多利亚/谢拉格/阿戈尔/叙拉古/卡西米尔/乌萨斯/伊比利亚/莱塔尼亚/萨尔贡）
   - 其他（罗德岛、哥伦比亚、莱茵生命、使徒、拉特兰、东、米诺斯、萨米、雷姆必拓、玻利瓦尔、杜林、企鹅物流、黑钢国际、彩虹小队、S.E.E.S.、Ave Mujica…）忽略
3. 去重、按核心盟约固定顺序排序
4. 结果为空 → ["协防干员"]
```

### 5.2 为什么把 `hiddenFaction` 也算进来

固定名单里有不少干员的**至少一个**核心标签要由隐藏阵营解释；以下是抽样（复奏/哈洛德/卡涅利安也属同类）：

| 干员 | ingameFaction | hiddenFaction | 主表核心标签 |
| --- | --- | --- | --- |
| 烛煌 | 罗德岛,罗德岛-精英干员 | 炎;;维多利亚 | 炎、维多利亚 |
| 水月 | 东 | 阿戈尔 | 阿戈尔 |
| 涤火杰西卡 | 哥伦比亚,黑钢国际 | 维多利亚 | 维多利亚 |
| 薇薇安娜 | 莱塔尼亚 | 卡西米尔 | 莱塔尼亚、卡西米尔 |
| 温蒂 | 罗德岛 | 伊比利亚 | 伊比利亚 |
| 锏 | 谢拉格,喀兰贸易 | 卡西米尔,莱塔尼亚 | 谢拉格、卡西米尔、莱塔尼亚 |
| 鸿雪 | 罗德岛 | 萨尔贡 | 萨尔贡 |
| 真言 | 罗德岛,罗德岛-精英干员 | 巴别塔,萨尔贡 | 萨尔贡 |

反过来，`塞雷娅（哥伦比亚,莱茵生命）`、`夜莺（使徒）`、`缪尔赛思（哥伦比亚,莱茵生命）` 没有任何核心阵营，主表给的是「坚守/聚合 + 协防」——与「无核心 → 协防」一致。

因此：

- **核心标签 =（ingameFaction ∪ hiddenFaction）∩ 10 个核心盟约**，这个口径能解释固定名单里的核心标签。
- **协防** 是「无核心」的兜底；固定名单里 初雪/塔露拉 也带协防，属于人工加的额外标签，不影响甄选规则（甄选按原文只给核心或协防）。
- **附加盟约**（精准/坚守/助力/不屈/聚合/奥术/迅捷/灵巧/远见/奇迹/投资人/突袭/调和/独行/绝技）不要从阵营推；甄选按原文不分配附加。

> 建议把上面的「固定名单回测」做成构建期硬门槛：对 143 条逐条比对「阵营推导出的核心标签」与主表 `盟约一~三` 的核心项；不一致就列进报告，超过阈值（如 3 条）直接失败。这样一旦 PRTS 改字段或赛季换阵营，能立刻发现。

### 5.3 需要实测确认的三点

1. **隐藏阵营是否参与甄选**：本方案默认参与（因为固定名单需要它）；若游戏内只认 `ingameFaction`，则 烛煌/薇薇安娜 等会变成「协防」。建议在数据里同时保留 `tagsDefault`（并集）和 `tagsVisible`（仅 ingameFaction），前端可切换/标注。
2. **多核心是否全给**：锏的并集是 3 个核心。固定名单是 3 个都给了；甄选是否也全给，需要一局实测。
3. **附加盟约**：原文只提核心/协防；若实测甄选也有附加，再加「职业/分支 → 附加」映射表，不要提前猜。

## 7. 推荐方案

### 7.1 数据模型

新增顶层 `picks`（只读、构建期生成）：

```json
{
  "picks": [
    {
      "key": "斩业星熊",
      "name": "斩业星熊",
      "charId": "char_1044_hsgma2",
      "rarity": 6,
      "class": "重装",
      "branch": "驭法铁卫",
      "factions": ["炎-龙门", "龙门近卫局"],
      "hiddenFactions": ["东"],
      "tags": ["炎"],
      "tagsSource": "faction-union",
      "prts": { "page": "斩业星熊", "url": "https://prts.wiki/w/斩业星熊" },
      "avatar": "assets/avatars/av-xxxx-96.webp",
      "avatarFull": "assets/avatars/av-xxxx-180.webp"
    }
  ],
  "pickMeta": {
    "season": "卫戍协议·规程",
    "source": "prts-cargo",
    "fetchedAt": "2026-11-10 17:00:00",
    "gameDataVersion": "26-11-06-12-56-09-07186384",
    "rule": "ingameFaction ∪ hiddenFaction → 核心盟约；空 → 协防干员"
  }
}
```

槽位状态：

```json
{ "k": "自选配置 6阶-1", "p": "斩业星熊", "e": false, "it": [] }
```

- `k` 保留占位行：提供阶数 V/VI、售价 4、席位身份。
- `p` 指向 `picks`：提供真实名字、头像、盟约、PRTS 链接。
- 不新增第 10 个字段给「精锐」——`e` 照旧。
- 不把 picks 塞进 `operators`：避免图鉴多出 60+ 条、分享码指纹大改。

### 7.2 构建管线

新增 `tools/fetch_pick_operators.py`：

1. 读主表「干员表」，拿到 143 个固定名字（排除 `type=自选配置`）。
2. 查 PRTS Cargo（一次请求，`limit=500`）：

   ```text
   action=cargoquery
   tables=chara,chara_data
   join_on=chara._pageName=chara_data._pageName
   fields=chara._pageName=name,chara.charId,chara.charIndex,chara.profession,
          chara.subProfession,chara.rarity,chara.nation,chara.org,
          chara_data.ingameFaction,chara_data.hiddenFaction
   where=chara.rarity=5 AND chara.charIndex>0
   ```

   > `charIndex>0` 会漏掉 `charIndex=0` 的专属干员（Pith/Sharp 等）。若要收「罗德岛特派」，改成 `charIndex>=0`，再按 `(卫戍协议)` 后缀 / 空阵营单独分组，别混进普通 6★。

3. 排除：固定名单、`(卫戍协议)` 专属干员、`预备干员-*`；罗德岛特派单独放 `reserve` 组（可选）。
4. 读 `data/faction_map.json`，按 §5.1 算 `tags`；空 → `["协防干员"]`。
5. **固定名单回测**：143 条逐条比对核心标签；输出 `build/pick_report.md`，不一致超过阈值即失败。
6. 可选：读 `build/character_table.json`（官方 slim 索引）核对 `charId / rarity=6 / nationId`；没有就跳过，只在报告里注明「未做解包硬校验」。
7. 写 `data/pick_operators.json`（含 `meta`），头像抓取沿用 `prepare_avatars.py` 的 PRTS `imageinfo` 流程（新增 `--picks` 或独立脚本）。

`build_web_data.py` 增加：

- `picks` 注入 `payload`；`counts.picks`。
- 校验：tags 必须在盟约表；picks 名字不得与固定干员重名；每条必须有 `charId`；数量低于阈值（实测 66 条，阈值建议 50）报错（防止抓取失败产出空表）。
- 报告追加：picks 数量、按盟约分布、固定名单回测结果、缺阵营/缺图清单。

### 7.4 判定（`calc.js`）

```js
var base = ops[s.k];
var pick = s.p && pickOf[s.p];   // pickOf：构建时生成的 name → pick 索引
var op = pick ? {
  name: pick.name, tags: pick.tags, price: base.price,
  tier: base.tier, tierLabel: base.tierLabel,
  avatar: pick.avatar, avatarFull: pick.avatarFull,
  pick: true, normalText: '甄选干员：无特质', eliteText: '甄选干员：无特质'
} : base;
```

- `tags` 用 pick 的；`price` 用占位行的 4；`e` 照旧；`it` 照旧（可装备）。
- 去重键改用实际名字（`pick.name`），防止两个甄选位选同一人。
- 附加盟约不参与；协防按现有 `special` 规则计数（2 人）。
- 调和：甄选干员不自动获得调和（除非 `tags` 里真给了，按数据走）。
- 绝技：精锐计数照旧（甄选可精锐）。

### 7.5 URL 与分享码

**URL**（`store.js`）：

```text
#/team?t=自选配置 6阶-1,...&p=,,斩业星熊&e=...&it=...&m=...&L=...
```

- `p` 与 `t` 等长、按席位、空段占位；`p` 里有值的席位必须 `t` 是自选配置行。
- 旧链接没有 `p`，行为不变。

**分享码**（`code.js`）：

- 建议升 **GSPA3**：在「干员下标」后加 1 bit `hasPick`；`hasPick=1` 时再写 8 bit 甄选下标（≤256 条足够）。
- 指纹 `tagOf` 加入 `picks` 名称，换赛季/名单变动会变，继续提示「跨期分享」。
- 保留 `GSPA2` 解码：旧码没有 `hasPick`，按无甄选处理；新码统一 `GSPA3.` 前缀，避免歧义。
- 测试：空队、8 人、9 人、含 1/2 个甄选、旧码导入、跨指纹提示。

### 8.2 准确度：固定 6★ 回测 75/76

把「阵营并集 → 核心盟约」套到 76 名固定 6★ 上：

| 仅 nation | 67 / 76 | 88.2% | 同上 |
| nation + org | 67 / 76 | 88.2% | 同上 |

唯一的 6★ 例外是 **克莱门莎**：`ingameFaction=阿戈尔`、`hiddenFaction=伊比利亚`，主表只给「阿戈尔」；并集会多算一个「伊比利亚」。这是「可见核心 + 隐藏核心」被忽略的案例——66 名候选里最接近它的是 **缄默德克萨斯**（可见炎 + 隐藏叙拉古），需要重点实测。

## 9. 风险与边界

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 甄选规则只写在 PRTS，未在游戏内逐条实测 | 隐藏阵营/多核心/附加可能偏差 | 数据里同时存 `tagsDefault`（并集）与 `tagsVisible`；前端标注推导依据；保留手动改盟约 |
| 「自身持有」无法校验 | 候选池包含玩家没有的 6★ | 只做「需自身持有」提示，不阻止选择；这是模拟器，不是账号工具 |

| 66 个新头像 | 体积增加（96px 约 0.3 MB，180px 约 0.9 MB） | 只给甄选干员抓 96px；180px 可选；`build_dist.py` 已有体积自检 |
| 分享码从 GSPA2 升 GSPA3 | 旧码/新码兼容 | 双解码 + 单测；指纹加入 picks |
| PRTS 字段改名/赛季换阵营 | 映射失效 | 固定名单回测做硬门槛；`pickMeta` 记录抓取时间；失败即中止构建 |
| 版权 | 头像/文本仍属鹰角/PRTS | 沿用现有非商业、可开关、收到异议即下线的口径 |
