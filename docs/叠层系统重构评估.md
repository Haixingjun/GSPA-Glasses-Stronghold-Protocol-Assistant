# 叠层系统重构评估

> 2026-11-12 更新：M0（基线/测试）与部分 M1/M2（stack-core、事件总线、Aegir/助力/售价）已落地，见 [叠层重构与文本审查报告.md](叠层重构与文本审查报告.md)。

- **日期**：2026-11-12
- **对象**：`web/js/sandbox.js`、`web/data/operator_rules.js`、`tools/test_sandbox.mjs`
- **参考方案**：[沙盒阿戈尔优化清单.md](沙盒阿戈尔优化清单.md)、[沙盒干员叠层对照清单.md](沙盒干员叠层对照清单.md)
- **性质**：评估与建议，**未改任何代码**。

## 0. 结论

| 问题 | 结论 |
|---|---|
| 难度有多大？ | **渐进式内核重构：中等（3/5）**；**照参考项目重写：高（5/5）**；只修 bug：低（1/5） |
| 是否建议重构？ | **建议重构，但只重构“叠层内核”，不推倒 UI/数据层**；采用绞杀者模式，分两期 |
| 建议投入 | 只修 bug + 阿戈尔：**2–4 人日**；持续加干员/机制：**10–17 人日**；完整参考式引擎：**6–12 周，不建议** |
| 前提 | 1 名熟悉代码的开发者全职投入；不改 UI 视觉；不做完整战斗数值（HP/ATK/DEF/status/ammo） |

**一句话**：值得重构，但不值得重写。当前叠层逻辑已经集中在 `addLayer()` / `applyRule()` 附近，适合“抽内核 + 加描述层”；照搬参考项目的 garrison/DSL/战斗引擎，会把 3k 行沙盒变成数万行、且大部分能力用不上。

## 1. 现状度量

| 指标 | 数值 | 含义 |
|---|---:|---|
| `sandbox.js` | 约 3,100 行 / 163 个函数 / 52 个渲染与交互函数 | 单体文件，但职责边界大致可辨认 |
| 叠层核心 | `addLayer` L1239–L1262、`computeRuleBase` L1317–L1332、`applyRule` L1355–L1448、`triggerEvent` L1568–L1609 | 约 370 行，是重构的主要抽取对象 |
| 状态/报表 | `state` L329–L340、`generateReport` L665–L709、`handleEvent` L2192–L2289 | 与 UI/报表/沙盒码耦合 |
| 规则数据 | `operator_rules.js` 304 条 / 143 名干员；`special` 164 条 / 80 名 | 数据是文本生成的，仓库里没有生成器 |
| 测试 | `tools/test_sandbox.mjs` 42 项 | 覆盖关键特殊干员，但缺少“机制矩阵”级回归 |
| 耦合点 | `addLayer` 5 处、`applyRule` 6 处、`state.layers` 11 处、`renderAll()` 27 处 | 核心函数调用点不多，**可抽取**；UI 直接读状态，需要兼容层 |
| 版本控制 | 2026-11-12 已移除 `.git/info/exclude`，沙盒文件纳入仓库 | 重构前建分支；改动可回滚/评审 |
| 构建 | 无打包步骤，ES5/IIFE + `script` 顺序加载 | 拆分后必须保持全局加载顺序，不能引入 bundler |

**判断**：叠层核心不像 UI 那样散落在 52 个函数里，`addLayer/applyRule` 的调用面很小；难度主要不在“把函数搬出去”，而在**数据描述、行为兼容、测试基线**。

## 2. 三种“重构”不是一回事

| 方案 | 范围 | 难度 | 预估 | 建议 |
|---|---|---|---|---|
| **A. 原地修复 + 小扩展** | 修 `battleStart`/报表/售价/事件误判；补阿戈尔吞噬 | 低（1/5） | 2–4 人日 | 如果近期只做阿戈尔，先做这个 |
| **B. 叠层内核重构** | 抽 `layer-store`/`event-bus`/`rule-engine`/`bond-effects`；加 descriptor、metrics、兼容层 | 中（3/5） | 10–17 人日 | **推荐**；分两期，保留 UI |
| **C. 参考式 garrison/DSL/完整战斗** | 249 条 garrison、9 战斗钩子、13 备战处理器、HP/ATK/DEF/status/ammo/召唤 | 高（5/5） | 6–12 周 | **不推荐**；与“层数沙盒”定位不匹配 |

> 参考项目的 151 条叠层记录 / 72 名干员，是**完整战斗模拟**的产物；它的价值是“描述能力”，不是“代码必须照搬”。

## 3. 为什么是“中等”，不是“低”

1. **没有规则生成器**：`operator_rules.js` 头部写“自动生成”，但仓库里没有生成脚本；304 条规则无法从 xlsx 重建。重构必须先把“生成器 + 校验”补上，否则只是把不可维护的文本规则换了个位置。
2. **测试基线不足**：42 项测试覆盖了关键特殊干员，但没有“所有事件 × 上限 × 目标”的矩阵；重构前要加 **characterization/golden tests**，锁定当前输出（包括错误行为），否则无法判断“重构后是否等价”。
3. **UI/报表直接读状态**：`renderAll()` 27 处、`state.layers` 11 处、`stackEvents` 8 处；抽内核时要提供兼容 facade（`getLayers()`/`subscribe()`/`getEvents()`），不能一次性改所有 UI。
4. **数据缺口**：售价（`sellPrice`）、调度中心等级、装备、状态（冻结/沉睡/眩晕/恐惧）、弹药、资金都没有模型；有些机制不是“加个字段”，而是要先补数据源。
5. **无构建、ES5/IIFE**：拆模块要手工维护 `sandbox.html` 的 `<script>` 顺序，不能用 ESM/bundler；这会限制“漂亮架构”的收益。
6. **已纳入 git（2026-11-12）**：`.git/info/exclude` 里的沙盒文件排除已移除；重构前建分支即可，改坏了能回滚。
7. **参考项目是 GPL-3.0，本项目 MIT**：只能按行为独立实现，不能复制 garrison/DSL 代码；这会让“照抄”实际上不可行。

## 4. 推荐的目标结构

保持“无构建、IIFE、script 顺序加载”，只拆 5 个文件：

```text
web/js/sandbox/
  state.js          // state.layers/temp、counters、metrics、快照
  layer-store.js    // addLayers()、999 封顶、stackEvents、订阅
  event-bus.js      // 事件注册/触发顺序、onMetric、onKnockdown
  rule-engine.js    // descriptor -> target/bonds/amount/cap -> 结算
  bond-effects.js   // 吞噬、助力、投资人、调和等盟约级钩子
web/js/sandbox.js   // UI/拖拽/渲染/报表，保留，调用 SandboxCore
```

对外 API（兼容层）：

```js
window.SandboxCore = {
  getState, addLayers, trigger, subscribe,
  getLayers, getEvents, getMetrics
};
```

约束：

- 不改变 `state.layers` 的语义；旧 UI 继续读 `state`。
- `rule-engine` 接受“旧规则”和“新 descriptor”两种输入，先适配旧数据，再逐步迁移。
- 所有新机制走 `event-bus`，不再往 `sandbox.js` 加 `if (name === 'xxx')`。
- 报表只读 `stackEvents`，不直接写层数。

## 5. 分阶段计划

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---:|
| **M0 基线** | 把沙盒文件纳入 git；跑 42 项；补 10–15 条 golden 测试（现有行为，含 bug） | 可回滚基线 | 1–2 人日 |
| **M1 抽纯函数** | `computeRuleBase`、`resolveTargets`、`resolveRuleBonds`、`capAura` 先搬，不改行为 | `rule-engine` 纯函数 | 2–3 人日 |
| **M2 抽状态/事件** | `addLayer` + counters + `triggerEvent` + `EVENT_LABEL` 搬到 `layer-store`/`event-bus`；UI 通过 facade | 内核与 UI 解耦 | 2–3 人日 |
| **M3 描述层** | 旧规则 -> descriptor 适配器；新 `onMetric`/`onKnockdown`；先接 9 名 special | 新机制可加数据 | 3–4 人日 |
| **M4 盟约级效果** | 吞噬、助力、投资人、调和；Aegir 吞噬按阶加层 | 盟约钩子 | 2–3 人日 |
| **M5 收尾** | 删旧分支、补测试、更新 `sandbox.html`/dist/文档 | 稳定版 | 1–2 人日 |
| **合计** | 不含 L0 的 4 个 bug 修复 | | **11–17 人日**（±50%） |

> 如果只做“阿戈尔 + 修 bug”，不需要走 M3–M5；M0 + 原地修 3–6 人日即可。

## 6. 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 行为回归 | 现有 42 项/用户配队结果变化 | 先 golden tests；新旧双跑对比；一次只迁一个机制 |
| 数据迁移错误 | 304 条规则中 special/文本误判 | 生成器 + 校验；保留旧数据回退开关 |
| UI 耦合 | 报表/弹层/沙盒码崩溃 | facade；不一次性改 UI；按 `state.layers` 只读兼容 |
| 范围蔓延 | 从“层数”滑到“完整战斗模拟” | 明确 out of scope：HP/ATK/DEF/status/ammo 先不做 |
| 数据缺口 | 售价/商店/装备/状态无法算 | 先加 metric 计数，不建实体；缺数据就显示“未模拟” |
| 许可 | 复制参考 GPL 代码 | 只按行为独立实现；记录参考链接，不复制源码/注释/测试 |
| 版本控制 | 改坏无法回滚 | 已移除 `.git/info/exclude`；重构前建分支；dist 重建 |
| 工期 | 10–17 人日只是内核，不含 UI/数据补齐 | 按 M0–M5 分期验收；每期可停 |

## 7. 决策建议

### 建议做

- 如果路线图还有“继续加干员/盟约/机制”（阿戈尔之后还有 11 名 special、40 条层数缩放、助力/投资人/调和），**做 B 方案**；否则每加一个机制都要改 `sandbox.js`，维护成本会持续上升。
- 先做 **M0 + L0 四个 bug 修复**（3–6 人日），再决定是否进入 M1–M5；这样即使停止，也已经有净收益。
- 把“数据生成器/校验”作为 M1 的前置，不要先搬函数再补数据。

### 不建议做

- **不要照参考项目重写**：完整 garrison/DSL/9 钩子/13 处理器/HP/status/ammo 是完整战斗模拟的产物；本项目没有全干员 HP/ATK/DEF 数据，硬接会得到“看起来完整、实际全是假设”的系统。
- **不要为了重构而重构**：如果目标只是修阿戈尔/几个 bug，原地修 + 小抽取即可；全量重构的收益要等“新增第 3–5 个机制”才明显。
- **不要一次性改 UI**：UI/报表/沙盒码是耦合最重的部分；保留现有渲染，只换数据源和事件入口。

### 什么时候才值得“新引擎”

满足以下任意两条，再考虑独立新引擎（而不是在 `sandbox.js` 里重构）：

1. 需要完整战斗数值（HP/ATK/DEF/block/status/ammo/召唤/复活）。
2. 需要跨赛季数据版本（act1/act2/规程）并存。
3. 需要服务端权威/多人/回放/确定性模拟。
4. 机制数量再翻倍（>30 类事件、>300 条规则），当前规则表已无法表达。

否则，**B 方案的 10–17 人日足够覆盖未来 1–2 个赛季的叠层扩展**。

## 8. 验收标准

- 42 项原测试 + 新增 ≥15 项（机制矩阵/金标）全绿。
- 同一输入下，重构前后 `state.layers`、`stackEvents`、报表输出一致；差异必须逐条解释。
- `sandbox.html` 无新增构建步骤；`dist/` 可重建；沙盒码往返一致。
- 新增一个机制只改数据/descriptor，不改 `sandbox.js` 的 UI 分支。
- 明确 `unsupported` 列表：未建模的 special 仍显示“未模拟”，不再静默。
- 代码纳入 git，有分支/回滚点；文档记录 descriptor schema 与 assumed。
