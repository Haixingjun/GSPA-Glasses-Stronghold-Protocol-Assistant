# 沙盒「其他干员叠层」对照与优化清单

> 2026-11-12 更新：售价、battleStart 幂等、助力、事件修正等已部分落地，见 [叠层重构与文本审查报告.md](叠层重构与文本审查报告.md)。

- **日期**：2026-11-12
- **参考项目**：[sganggs/Stronghold-Protocol](https://github.com/sganggs/Stronghold-Protocol) @ `f07b896`（2026-10-25，act1/act2 口径，比本项目当前赛季早）
- **对照对象**：`web/data/operator_rules.js`、`web/js/sandbox.js`、`web/data/data.js`、`tools/test_sandbox.mjs`
- **性质**：只做对照与方案，**未改动任何代码或数据**；本文是唯一新增文件。
- **关联**：阿戈尔的专属方案见 [沙盒阿戈尔优化清单.md](沙盒阿戈尔优化清单.md)；本文覆盖其余干员与通用叠层机制。

## 0. 结论（先看五条）

1. **参考项目不是“每个干员写一段叠层代码”，而是一套通用的数据驱动层系统**：`data/garrisons.json` 里 151 条与叠层相关的记录（140 条能映射到有载体干员：64 条 `IN_BATTLE` + 76 条 `SERVER_*`；另有 9 条仅被授予、2 条增幅）覆盖 72 名干员，由 `server/sim/content/garrisons/battle.js` 的 9 个战斗钩子和 `garrisons/meta.js` 的 13 个休整期处理器统一执行。新增干员通常只加数据，不改引擎。
2. **本地不是“没实现”**：`operator_rules.js` 有 148 条可结算叠层规则 / 71 名干员（含 `EXTRA_RULES` 的 10 名），另有 22 条 / 11 名仍是 `special` 文本。问题主要在**事件源**——被击倒、状态进入、元素爆发、弹药、资金、调度中心等级、装备、售出这 8 类事件没有入口，而不是 `addLayer` 本身。
3. **有 4 个确定性缺陷会直接算错**：`battleStart` 非幂等（烈夏可无限叠临时层并重置 `perBattle` 额度）；休整期报表在 `onBattleStart` 之后生成；旅骨/棘刺的“售出价格”用了采购价；部分规则的事件被文本生成器误判（远牙、耀骑士临光、归溟幽灵鲨、风丸、历阵锐枪芬）。
4. **盟约级乘数没接，影响所有干员**：助力（休整期结束所有已激活盟约 +2/+4）、投资人（“获得时”×2/×3）、调和（核心盟约人数 +1 且享受核心效果）。这三条不补，单个干员的层数算得再准，总量仍会偏低。
5. **同名 22 名干员里，5 名是同机制但数值/上限不同，17 名是赛季 kit/名单差异**。参考项目的阿戈尔、幽灵鲨、斯卡蒂、史尔特尔等已经是另一套 kit；**不要照抄参考数值**，只借鉴机制与测试。

## 1. 两套实现范式

| 维度 | 参考项目 | 本项目沙盒 | 结论 |
|---|---|---|---|
| 数据形态 | `garrisons.json`：`eventType` + `effectType` + `effectKey` + `bb/bbStr` + `owners`；一条记录可被多名干员拥有 | `operator_rules.js`：按干员名组织的 `event/bonds/amount/caps`；`EXTRA_RULES` 再硬编码 13 人 | 参考是“规则数据”，本地是“按干员生成的规则表” |
| 叠层入口 | `ADD_BOND`（战斗中）、`SERVER_ADD_BOND*`（休整期/获得/售出/刷新）、`SERVER_ADD_BOND_METHOD`（按等级/获得/手牌/同行/不同阶） | `applyRule()` 统一处理 `bonds/amount/perRound/perBattle/...` | 入口数量接近，但本地缺少事件源与组合字段 |
| 事件源 | skillStart、kill（每 N 个）、death/doll swap、ammoUsed、statusApplied(freeze/sleep/stun)、elementBurst、every deploy、shop level、round spend、refresh、sell | onSkill/onKill/onDeploy/onGain/onRefresh/onPrepStart/onPrepEnd/onBattleStart/onBattleEnd | 本地缺 8 类事件 |
| 上限 | `max_add_count_per_battle`、`check_cnt`、`capKey`（按实例/盟约） | `perRound/perBattle/perTotal` + `capAura`，键含目标/盟约/规则 | 本地上限模型够用，但缺“每 N 次触发”和“逐盟约不同数额” |
| 目标选择 | 自身/前/后/自身+前/自身+后/整备区/同行最右/所有同标签/所有前方 | 自身/前/后/自身+前/自身+后/周围 4/8/整备区 | 缺“所有前方”“同行最右”“所有同标签” |
| 授予特质 | `ADD_BOND` 可把另一个 garrison 授予前/所有/自身+前/同行最右，带每场上限 | 仅华法琳 `grantFrontTrait`（只前 1、只战斗开始、只定值）+ 铃兰 `triggerFrontGain` + 荒芜 `teamWide` | 缺通用 `grantTrait` |
| 测试 | `test/content/garrisons_battle.test.js`、`garrisons_meta.test.js` 等专用矩阵 | 42 项；对 13 名 `EXTRA_RULES` 有零散断言，无通用机制矩阵 | 本地缺“事件源 × 上限 × 目标”的系统测试 |
| 数据可维护性 | 官方记录编译为 garrison，事件/数值/目标都在数据里 | 文本生成器不在仓库；`operator_rules.js` 头部写“自动生成”，但无法重建 | 文本关键字会误判（见 §8） |

**一句话**：参考项目强在“事件与数据的通用性”，本地强在“轻量、可读、无战斗模拟负担”。本方案不搬 garrison 引擎，只搬它的**描述能力**。

## 3. 机制矩阵（核心）

状态：**支持** = 有事件入口 + 通用字段 + 上限；**部分** = 能算但有硬编码/单目标/无计数；**缺失** = 无事件或无模型。

| # | 参考风格触发 | 判定 | 本地依据 / 缺口 | 代表干员 |
|---|---|---|---|---|
| 1 | 开技能加层（skillStart） | ✅ 支持 | `onSkill`（`sandbox.js:2244-2250`）；`perRound/perBattle` 齐全 | 艾丝黛尔、泡泡、陨星、鸿雪 |
| 2 | 击倒敌人加层（每 1 名） | ✅ 支持 | `onKill`（`:2178-2190`）；`inRange` 靠 `ctx.enemy` 格子 | 地灵、黑键、遥、冻河 |

**结论**：本地 `addLayer`、上限、目标、`capAura` 已经够用；真正缺的是 **#3–#9、#13 shoplv、#15–#18、#20–#21、#23–#24** 这些“事件源/组合字段”。

## 4. 盟约级乘数：优先于补单个干员

这三条不是某个干员的规则，但会改变所有干员的层数总量，优先级应高于 §5 的 11 名 special。

| 盟约 | 参考实现 | 本地现状 | 影响 |
|---|---|---|---|
| **助力** `deputShip` | `bonds/addon/meta.js`：`onPrepEnd` 给**所有已激活盟约** +2；3 名不同（或精锐）改 +4 | `sandbox.js` 无任何 `助力` 钩子；只有罗比菈塔的 `bonds:['坚守','助力']` 会顺带加 | 每回合少 2–4 层 × 所有激活盟约；6 个盟约就是 12–24 层/回合 |
| **投资人** `investShip` | `server/match/effectsMeta.js` `investRepeat()`：所有 `SERVER_GAIN`（“获得时”）×2；≥100 层 ×3 | `sandbox.js` 无 `投资人` 逻辑；`onGain` 只结算一次 | 灰喉 +2 精准会变 +4/+6；锡人 +4 投资人会变 +8/+12 |

> **注意双重翻倍**：本地 `锡人` 的 `onGain 投资人 +4/+8` 可能已经内建了“投资人 ×2”（参考同源记录是 +2/+4）。接入全局 ×2 前，需要把锡人改回 base +2，或给它加 `investMultiplierAlreadyApplied` 标记；否则会变成 +8/+16。灰喉等其他 `onGain` 也要逐一确认是否已内建倍率。
| **调和** `maniShip` | `bondsMeta.js`：核心盟约人数 +1；调和干员享受核心盟约效果（`isMember`） | `calc.js` 只给核心盟约 `count +1`（`harmonyBonus`）；`opTags` 不把调和当核心成员 | 调和干员拿不到阿戈尔吞噬/谢拉格层数等“成员效果”；阿戈尔 5 人 + 调和可到 6 人强化，本地只算激活人数 |

补充：

- **远见/奇迹**：参考有层数里程碑（每 10/100 层发钱、80/150 层降价），本地层数手填、无经济结算。若沙盒只做层数，可暂不做；但盟约弹层应显示当前层数与下一节点。
- **阿戈尔**：吞噬/复活见 [沙盒阿戈尔优化清单.md](沙盒阿戈尔优化清单.md)；本文不重复。

## 7. 同名 22 人：5 个同机制，17 个赛季差异

22 名两边都有叠层记录（按精确中文名匹配）：

- 本地 143 人的 `normalText/eliteText` 与规则字段已做一致性校验（上限/单次/盟约名四类），未发现内部矛盾；22 人里 12 人阶数也被重定（史尔特尔 5→6、夕 5→6、引星棘刺 5→6、寒檀 5→4、安洁莉娜 5→4、流明 6→4、纯烬 6→5、拉普兰德 2→1、幽灵鲨 2→1、折桠 2→1、蛇屠箱 3→2、雪猎 3→2），数值差异大多随阶数/赛季走。

## 8. 本地确定性缺陷（建议随 P0 一起修）

### 8.1 `battleStart` 非幂等

`sandbox.js:2217-2223`：

```js
if (name === 'battleStart') {
  if (state.phase !== 'combat') return;
  state.battleCounters = {};
  triggerEvent('onBattleStart');
  logBattleCapAuras();
  return;
}
```

问题：

- 重复触发会再次执行 `onBattleStart`。烈夏的规则是 `onBattleStart + 乌萨斯 temp +4/+8`，**没有上限**，可被重复点到无限临时层。
- 重置 `battleCounters` 会“洗掉”所有 `perBattle` 已用额度，导致同一场战斗的上限可以刷第二次。

补充：当前 `sandbox.html` 没有 `data-event="battleStart"` 按钮，普通用户点不到；但 `handleEvent('battleStart')` 在测试/外部调用/未来加按钮时可用，属于“埋着的”确定性缺陷。

建议：`battleStartDone` 幂等；重复触发只提示“本场战斗已结算战斗开始”；`battleCounters` 只在 `prepEnd` 进入战斗时重置一次。

### 8.2 休整期报表时点

`sandbox.js:2210-2213` 是 `onPrepEnd → onBattleStart → logBattleCapAuras → generateReport('休整期')`。这样 `onBattleStart` 产生的层（烈夏、未来的吞噬/特质）会被算进“休整期报表”。

建议：`onPrepEnd` 后先生成“休整期”报表，再 `beginBattle()`；战斗开始的层归“作战期”或单列“战斗开始”小计。

### 8.3 售价类叠层用了采购价

`旅骨`：`<休整期结束时>使自身及身前一格干员已激活的盟约叠加等同于其售出价格的层数`；`棘刺`：`...场上所有干员售出价格...`。

本地实现：

- `EXTRA_RULES['旅骨']` 用 `priceTarget: true`（`sandbox.js:154-155`）；
- `棘刺` 用 `priceSum: true`；
- `computeRuleBase` 的 `priceTarget/priceSum` 都走 `opPriceOf()` / `boardPriceSum()`（`:1200-1210`、`:1327-1329`），取的是 **`meta.price`（采购价）**。

本地 `data.js` 没有 `sellPrice` 字段（0 名干员有）。参考项目的 `chess.json` 里 `sellPrice` 与 `price` 明确不同：示例 `price 2/3/4 → sellPrice 1`；温蒂/海沫还能改售出价格。

**影响**：旅骨/棘刺会按 2–4 倍采购价加层；若售出价是 1，棘刺在 8 人场上应 +8（精锐 +16），本地会按采购价合计 +20 左右。**这是一个确定性算错**，不是赛季差异。

建议：数据补 `sellPrice`（含海沫/温蒂修正），`priceTarget/priceSum` 改读售出价；加测试。

### 8.4 文本生成器的事件误判

`operator_rules.js` 的 `event` 是从文本推出来的，不是官方 `eventType`。已确认的误判：

| 干员 | 本地 event | 文本实际触发 | 应改为 |
|---|---|---|---|
| 远牙 | `onDeploy` | “攻击范围内每有一名敌人被击倒…” | `onKill`（“再部署时间”里的“部署”误导） |
| 耀骑士临光 | `onKill` | “被击倒时召唤…” | `onKnockdown` |
| 归溟幽灵鲨 | `onKill` | “自身被击倒或与替身发生替换时…” | `onKnockdown` / `onSubstitute` |
| 风丸 | `onKill` | “自身被击倒或与傀儡发生替换时…” | `onKnockdown` / `onSubstitute` |
| 历阵锐枪芬 | `onDeploy` | “被击倒时召唤…” | `onKnockdown` |

这些规则目前要么是 `special`（不会误结算），要么是 `onKill` + `special` 混合；一旦接入 `onKnockdown`，必须先修事件，否则会“击倒敌人时触发自家被击倒效果”。

建议：`operator_rules.js` 增加 `eventSource`/`triggerText` 字段；生成器用“触发词表 + 人工复核”而不是纯关键字；对 `被击倒`、`再部署`、`敌人被击倒` 做专门测试。

### 8.5 `onSell` 只有文案，没有派发

`EVENT_LABEL` 有 `onSell`（`sandbox.js:114`），但 `handleEvent` 没有分支，`retreat()`（`:1993-2012`）也不派发。9 条 `onSell` special 规则既不算，也不会出现在事件日志；只在干员详情里显示“未模拟”。

建议：`retreat` 时派发 `onSell`（如果产品语义是“撤退=售出”）；或明确拆成“撤退/售出”两个事件。优先级低于层数主链路，但应在 P1 补。

### 8.6 `layerGainAura` 的逐盟约加成需确认

`applyRule` 在 `for (bonds)` 内逐盟约调用 `layerGainBonus(target)`（`:1411-1436`）。一条规则同时加两个盟约时，阿米娅的 `+1` 会生效两次。文本是“每次提升的层数额外+1”，如果“一次提升”指一次事件而非一个盟约，则本地会多算。建议加测试/在 `assumed` 记录；不要直接改。

### 8.7 `inRange` 字段未被读取

`operator_rules.js` 有 10 条 `inRange: true`，但 `applyRule` 的范围过滤只看 `ctx.enemy`（`:1399-1401`），不读 `rule.inRange`。当前“点格子击倒”时语义等价；但“点干员击倒”/`teamWide` 时 `noCell` 跳过范围，`inRange` 字段形同虚设。建议删除该字段或真正实现。

### 8.8 部分规则缺 `text`，展示退化

`operator_rules.js` 中 安洁莉娜（4 条）、寒檀（4 条）、流明（2 条）等规则没有 `text` 键（全表共 6 人如此，另含华法琳/棘刺/薇薇安娜），而 `data.js` 同干员 `normalText/eliteText` 完整。`ruleTextOf()`（`:2438-2444`）会退化成 `<休整期结束时>【叙拉古】+2`，丢掉“本回合每进行过 1 次刷新”和上限语境，用户无法核对结算说明。

建议：生成器必须带 `text`（或 `triggerText`）字段；`ruleTextOf` 找不到时回退到 `data.js` 的 `normalText/eliteText`，而不是拼一个简化句。

### 8.9 荒芜拉普兰德的“幽灵规则”

`operator_rules.js` 里荒芜拉普兰德有第三条：

```js
{ event: 'onKill', special: '（晋升为精锐状态时，使所有【叙拉古】干员获得此效果）', elite: false }
```

它没有 `bonds/amount`，却挂在 `onKill` 且 `elite:false`；`ruleSummaryHtml` 会在**普通态**把它列为“未模拟特殊效果”，精锐态反而看不到；`applyRule` 首行 `if (rule.special) return 0` 说明它永不结算。建议并入精锐那条的 `text`，不要留成独立规则。

### 8.10 合并触发导致的语义丢失（砾 / 伺夜）

- **砾**：参考拆成“部署 卡西米尔 +1”与“被击倒 不屈 +2”两条；本地合并成一条 `onDeploy` 双盟约各 +2（`operator_rules.js` 的砾条目），导致“被击倒”前置消失、不屈被当成部署收益。
- **伺夜**：参考拆成“叙拉古 +2”与“奇迹 +1”两条；本地合并成一条双盟约 +2。若本季只是把奇迹换成精准，第二盟约可能被高估 1 层/次；需按 xlsx 原文核对，**不要直接改**。

建议：数据层支持“一条文本拆多条记录”，但每条记录保持单一触发/单一盟约/单一数值；合并只发生在展示层。

### 8.11 待核对：瑕光 / 寒檀的 0.75×

瑕光本地 `3/9` 对参考 `4/12`，寒檀本地 `3/6` 对参考 `4/8`，都是整齐的 0.75×。它们可能是本赛季按阶数/平衡调整，也可能是生成器读到了另一版表；建议在 §9 的数据核对里单独确认，**先不要按参考改**。

## 10. 建议的 descriptor schema

不引入参考项目的完整 DSL，只加一层“可结算描述”：

```js
{
  id: 'shengling-chuxue-freeze',
  owner: '圣聆初雪',
  elite: false,

  event: 'onMetric',            // onMetric | onKnockdown | onSell | onSkill | onKill | onDeploy | onGain | onPrepStart | onPrepEnd | onBattleStart
  metric: 'status:freeze',      // 仅 onMetric：status:freeze|sleep|stun|fear, element:burst, equip, gold:spent, kill
  per: 1,                       // 每 per 个 metric 触发一次（溯光星源 = 3）

  target: 'self',               // self | front1 | behind1 | selfAndFront1 | selfAndBehind1 | bench | around4 | around8 | knockdownUnit | summoned
  bonds: ['谢拉格'],             // 或 'active' | 'activeCore' | 'highestActive' | [{ name, amount }]
  amount: 1,                    // 标量；或 { per: 'targetTier' | 'shopLevel' | 'kill', mul: 2 }

  condition: {
    requireActive: true,
    phase: 'combat',
    inRange: true,              // 需要时用 ctx.enemy 的格子射程
    sameRow: null,              // 布尔阈值（P1）
    equipped: false             // 涤火杰西卡（P1）
  },

  cap: { perRound: 24, perBattle: null, perTotal: null, perInstance: true }
}
```

运行时：

```js
state.metrics = {
  'status:freeze': 0, 'status:sleep': 0, 'status:stun': 0, 'status:fear': 0,
  'element:burst': 0, 'equip': 0, 'gold:spent': 0, 'kill': 0
};
// value = amount * floor(metric / per)
// 再按 cap 扣额度，最后 addLayer()
// metric 的 scope：round -> prepStart/battleEnd 清；battle -> prepEnd/battleStart 清
```

关键约束：`metric` 只做**计数**，不引入敌人实体/HP；这样“状态进入/元素爆发/装备数”这类规则不需要完整战斗模型就能算对层数，和 Aegir 清单“P0 只算层数”的范围一致。

### 12.4 术语

- **可结算叠层**：有 `event` + `bonds`/`amount`，且 `applyRule` 能走完的规则。
- **special**：只有 `special` 文本、`applyRule` 直接跳过的规则。
- **metric**：本文建议的事件计数源（冻结次数、元素爆发次数等），只计数、不建敌人实体。
- **逐盟约数额**：一条规则对不同盟约给不同层数（如烛煌 炎/维多利亚 2/2 是相同；伺夜 叙拉古/奇迹 2/1 是不同）。
- **每实例上限**：同一条规则对每个目标/盟约独立计算上限，而不是全局共享。
