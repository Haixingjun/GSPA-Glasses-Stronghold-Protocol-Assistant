## 0. 一句话结论

**这一步是纯前端工作，`卫戍协议数据表.xlsx` 和 `build_web_data.py` 一行都不用改**——盟约的激活口径在构建时已经算好并写进了 `data.json`，配队只需要「收集 6 个槽位 → 按标签计数 → 套用 5 类判定 → 渲染」。

建议拆成 3 轮、约 3–4 个工作日：**R1 地基（计算内核 + 状态）→ R2 可用（板面 + 结果面板 + 选人）→ R3 好用（图鉴入口、整备区、分享、移动端打磨）**。

风险不在写代码，在**口径**：这套工具一旦给出错误结论，比不给结论更糟。所以规则集中在一个纯函数文件里、每条都能被单测钉住，并且页面上写明「本工具的口径」。

### 1.2 数据侧结论：够用，不用改表

`data.json` 里每个盟约已经有完整判定元数据（`tools/build_web_data.py` L334–409 生成）：

```json
{ "name": "炎", "rank": "core", "family": "faction", "garrison": false,
  "activation": { "kind": "count", "threshold": 3, "nodes": [],
                  "empower": ["在场6名不同【炎】干员"], "empowerThreshold": 6 } }
```

| 字段 | 含义 | 配队用途 |
| --- | --- | --- |
| `activation.kind` | `count` / `count_layer` / `elite` / `special` | 选判定分支 |
| `activation.threshold` | 激活人数（主盟约 3、副盟约 2、精锐 2） | 激活门槛 |
| `activation.empowerThreshold` | 强化人数（6 / 3 / 5） | 强化门槛 |
| `activation.nodes` | 层数节点（远见 10·80·150 等） | 层数进度 |
| `garrison` | 整备区是否计入（远见 / 奇迹 / 投资人） | 决定整备区是否参与计数 |
| `cond` | `BOARD` / `BOARD_AND_DECK` / `BOARD_ALL_CHESS` | 同上，备用 |
| 干员 `tags` / `tier` / `price` / `eliteText` / `normalTriggers` | — | 计数、总价、精锐效果、触发覆盖 |

现成统计（已核对 `data.json`）：干员 155 条（其中 **12 行是 `type: 自选配置` 的空壳**，无标签无头像）、26 个盟约、主盟约 10 个各 10 名成员、副盟约 9–14 名、独行 3 名、调和 2 名、绝技 0 名成员。

## 2. 目标与非目标

**做（P0）**

1. **6 个场上席位**（席位数可调 4–10），每个席位放一名干员，可切普通 / 精锐。
2. **整备区**（独立于场上席位）：默认关闭；开启后只对 `garrison: true` 的 3 个盟约计入。
3. **实时结果面板**：26 个盟约的「已激活 / 已强化 / 差 N 人」、精锐数、总售价、触发时机覆盖。
4. **层数手动输入**：给 6 个 `count_layer` 盟约填层数，点亮节点。
5. **选人**：点空位 → 抽屉里搜索 + 按阶数 / 盟约 / 售价筛 → 选中填入；图鉴卡片上加「+」直接入队。
6. **分享**：队伍状态进 URL，复制即还原；换设备打开即恢复。
7. **移动端**：底部 tab 加第 5 项；板面单列、结果面板折叠。

**不做（明确划掉）**

- 商店概率、经济曲线、升级费用推演（数据里没有，属于 §9 待确认以外的第二类问题）。
- 装备搭配、策略选择、战场敌人联动（下一轮，见 §10）。
- 账号 / 云端收藏 / 队伍广场（需要后端）。
- 拖拽排序。6 个槽位用点击即可，拖拽在移动端收益为负。

## 4. 规则与算法

### 4.1 输入模型

```js
team = {
  board: [ { key: '折桠', elite: false }, null, ... ],   // 长度 = boardSize（默认 6）
  bench: [ { key: '远见干员', elite: true }, ... ],       // 整备区，长度可变
  layers: { '远见': 80, '迅捷': 40 }                      // 仅 count_layer 盟约
}
```

干员的 `key` 就是 `name`（`data.json` 里两者恒等），URL 里直接放名字。

### 4.2 判定表（26 个盟约分 5 类）

| 类型 | 盟约 | 激活 | 强化 | 备注 |
| --- | --- | --- | --- | --- |
| `count` 主盟约 | 炎 / 萨尔贡 / 维多利亚 / 谢拉格 / 阿戈尔 / 叙拉古 / 卡西米尔 / 乌萨斯 / 伊比利亚 / 莱塔尼亚 | 带该标签 ≥ **3** 人 | ≥ **6** 人 | 各 10 名成员，凑 6 人理论可行 |
| `count` 副盟约 | 精准 / 坚守 / 助力 / 不屈 / 聚合 / 奥术 | ≥ **2** 人 | ≥ **3** 人 | 9–14 名成员 |
| `count_layer` | 迅捷 40 / 灵巧 40 / 远见 10·80·150 / 奇迹 100 / 投资人 100 / 突袭 50 | ≥ 2 人（投资人 3 人） | 层数节点 | **层数是手动输入**，不参与激活门槛 |
| `elite` | 绝技 | 精锐 ≥ **2** 名 | ≥ **5** 名 | 与标签无关，0 成员 |
| `special` | 独行 / 调和 / 协防干员 | 见下 | — | 不能套 `count >= threshold` |

`special` 三条必须**单独分支**，不许偷懒：

| 盟约 | 规则 | 状态 |
| --- | --- | --- |
| 独行 | 场上【独行】恰好 1 名时生效；≥2 名时**全部失效** | `active` / `inactive` / `conflict` |
| 调和 | 场上【调和】≥1 时激活，并给**每个主盟约 +1 人** | `active`（并作为其他盟约的修正项） |
| 协防干员 | 场上【协防干员】≥2（以表内人数列 2 为准） | `active` / `inactive` |

### 4.3 计算流程

```js
function evaluate(team, opts) {
  const board = team.board.filter(Boolean).map(slot => opByKey[slot.key]);
  const bench = opts.benchOn ? team.bench.filter(Boolean).map(...) : [];

  const tagCount  = countTags(board);              // 每个标签 1 人 1 票
  const benchTags = countTags(bench);              // 只给 garrison 盟约用
  const eliteCount = board.filter(s => s.elite).length;  // 只看场上

  // 调和修正（先算，因为主盟约要用）
  const harmony = tagCount['调和'] || 0;
  const harmonyActive = harmony >= 1;
  const bonus = harmonyActive && opts.harmonyMode === 'count' ? 1 : 0;

  return covenants.map(c => {
    if (c.activation.kind === 'elite')      return judgeElite(c, eliteCount);
    if (c.activation.kind === 'special')    return judgeSpecial(c, tagCount, harmony);
    if (c.activation.kind === 'count_layer') return judgeLayer(c, count(c, tagCount, benchTags), team.layers[c.name]);
    return judgeCount(c, count(c, tagCount, benchTags) + (c.rank === 'core' ? bonus : 0));
  });
}

function count(c, tagCount, benchTags) {
  return (tagCount[c.name] || 0) + (c.garrison ? (benchTags[c.name] || 0) : 0);
}
```

输出每一项：

```js
{ name, rank, kind, count, threshold,
  state: 'inactive' | 'near' | 'active' | 'empowered' | 'conflict',
  missing: number,          // 差几人激活（0 表示已激活）
  missingEmpower: number,   // 差几人强化（无强化档则为 null）
  node: number | null,      // count_layer：已达成的最高节点
  members: ['折桠', ...] }  // 场上实际贡献者，用于「为什么是 4/3」
```

排序：`empowered > active > near（miss ≤ 2）> inactive`，同级按 `rank`（主→副→特殊）、再按 `memberCount`。

### 4.4 边界与警告

| 情况 | 处理 |
| --- | --- |
| 同一干员重复上场 | 计算时**只算 1 次**，并在顶部警告「重复：折桠 ×2」 |
| 队伍里有 `type: 自选配置` | 默认不进候选池；若强行加入，标灰并提示「无标签，不参与盟约计数（待确认）」 |
| 隐藏条目（盟约·辅助干员 / “暴躁铁皮”） | **允许选**（它们是 调和 / 协防 的唯一来源），标签加「隐藏」角标 |
| 席位数被调小、已有干员超量 | 保留数据、标红「超出席位」，不静默丢弃 |
| 某盟约 0 人 | 不出现在「差一点」里，只在「全部」折叠区 |
| 精锐态干员的效果文本为空 | 沿用图鉴的「—」处理 |
| 层数为空 | 视为 0，节点全灭，不报错 |
| URL 里有未知干员名 | 丢弃该槽位并 toast 一次，不整队失效 |

### 4.5 口径可配置项（写进计算内核的 `RULES` 常量，页面上可见可改）

| 项 | 默认 | 取值 | 为什么要可配 |
| --- | --- | --- | --- |
| `boardSize` | 6 | 4–10 | 游戏内可能随调度中心等级变化 |
| `benchOn` | false | on/off | 整备区容量未知 |
| `benchSize` | 6 | 0–10 | 超过只警告、不阻断 |
| `harmonyMode` | `count` | `count` / `threshold` | 「+1 人」还是「门槛 −1」，对强化档有区别 |
| `harmonyStack` | false | false / true | 两个调和是否叠加 |
| `eliteInBench` | false | — | 整备区的精锐是否计入绝技 |
| `includeFlex` | false | — | 自选配置是否进候选池 |

## 5. 状态与 URL

沿用现有协议，新增 4 个参数（只在非空时输出）：

```
#/team?t=<slot>,<slot>&b=<slot>&L=<盟约>:<层数>&bs=<席位数>

slot        := <encodeURIComponent(干员名)>[*]      // * = 精锐
t           := 场上席位，按顺序，空位移除（不保留占位）
b           := 整备区
L           := 远见:80,迅捷:40                       // 名字 encodeURIComponent
bs          := 仅当 != 6 时输出
```

例：`#/team?t=%E6%8A%98%E6%A1%A0,%E8%AF%97%E6%80%80%E9%9B%85*,...&L=%E8%BF%9C%E8%A7%81:80`

- **队伍状态在非配队视图也输出**：这样「在图鉴里加了两个人 → 刷新 → 队伍还在」，分享链接也不会丢队。代价是图鉴链接会带 `t=`，可接受。
- **`localStorage` 只做兜底**：URL 里没有 `t` 时才读本地存档并回写 URL；URL 优先，避免两个真相源。键名 `gs-team`，与 `gs-theme` / `gs-avatars` 同风格。
- 编解码单元测试必须覆盖：中文名、含空格（`自选配置 5阶-1`）、含 `·`（`维娜·维多利亚`）、引号（`“暴躁铁皮”`）、`Miss.Christine`、`Mon3tr`。
- ⚠ **编码安全隐患**：`encodeURIComponent` 不会转义 `*` `,` `~`，所以用它们当分隔符/标记会有歧义。建议在 `build_web_data.py` 加一条构建期校验：**干员名不得包含 `,` `*` `~`**（现表全部满足），把风险钉死在数据侧，而不是在 URL 里做转义地狱。

## 9. 需要你拍板的 6 个问题

1. **场上席位是 6 吗？** 是否随调度中心等级变化（4 → 5 → 6）？要不要在口径里做「按等级切换」？
2. **整备区容量多少？** 是否真的只有远见 / 奇迹 / 投资人计入（我按 `garrison` 标记实现）？超出容量是警告还是禁止？
3. **调和 +1 到底怎么算**：给每个主盟约各 +1？两个调和叠加吗？是加人数还是降门槛（影响强化档 6 人）？
4. **「自选配置」12 行要不要参与配队？** 若参与，它游戏内是「指定任意 V/VI 干员」，盟约标签应该按指定者算——这需要额外输入，建议 P1 再做，先默认排除。
5. **精锐态是否仍计入原盟约标签？** 精锐是否只能靠「升华」类效果获得（决定要不要显示升级成本）？
6. **主要使用场景**：「开局前规划阵容」还是「对局中查还差几个」？前者要推荐、可以慢；后者要极简输入、结果一眼可见。这决定 R2 的结果面板是「全量列表」还是「只显示差 1–2 人的」。

## 10. 附：为什么这样切

- **不引入框架**：`开发说明.md` §9.3 明确「视图代码超 1500 行或需要拖拽 + 撤销 + 对比时才迁 Vue」。配队用点击不用拖拽，独立成 `team.js` 后总量约 1400 行，还没到点。为 6 个槽位引入 Vue 是净负债。
- **不先做推荐**：推荐算法依赖口径正确；口径没确认就做推荐，等于把错误放大 5 倍。所以推荐放 P1。
- **不改数据表**：`activation` 元数据已经在，改表只会引入「重建 Excel → 重跑校验 → diff 报告」的额外风险，收益为零。
- **不做拖拽**：6 个槽位点击两次就能填完，拖拽在手机上还会和滚动打架。
