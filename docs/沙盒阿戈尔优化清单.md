## 0. 结论（先看五条）

1. **本项目沙盒目前没有“阿戈尔盟约效果”，只有“阿戈尔标签 + 手工层数”。** `isBondActive('阿戈尔')` 只用于判断是否激活；`data.js` 里的阿戈尔 `desc/valueText` 只用于展示，没有任何代码执行“战斗开始时吞噬”。
2. **参考项目的阿戈尔实现是一套完整的盟约效果层**：`bonds.json` 的 `bb/spec` 提供参数与算法，`server/sim/content/bonds/core.js` 的 `devour()` / `installEgir()` 负责战斗开始吞噬、连链、层数、复活，`test/content/bonds_core.test.js` 等测试覆盖边界。这套“数据 + 盟约钩子 + 算法 + 测试”的结构值得借鉴。
3. **但参考项目所用阿戈尔数据（3/5、9 人）与本项目当前赛季不同**：本项目 2026-11-06「规程」数据为 **3/6、10 名成员**。参考项目里幽灵鲨/斯卡蒂/归溟幽灵鲨/克莱门莎的叠层来源也与本地不同。**只能借鉴机制，不能照抄数值、名单或干员 kit。**
4. **吞噬的层数口径可以先不做 5000 流失/退场模型。** 吞噬的标记在伤害结算前全部放置；每个“被标记的不同单位”每场只加一次“其等阶”的层数。对**吞噬本身**的层数总量而言，目标是否被 5000 流失击倒通常不改变“被标记集合”；唯一例外是战斗开始前已退场的单位（联防），本沙盒没有这个状态。因此 **P0 只做标记/顺序/连链/去重/层数**，就能把吞噬层数算对；HP、DEF、死亡、复活，以及克莱门莎策略等“被击倒加层”来源放到 P1/P2。
5. **合规提醒**：参考项目代码是 **GPL-3.0-or-later**，本项目是 **MIT**。不要复制其源码、注释或测试代码；按官方描述与可观察行为独立实现，本文只作为行为参考与验收依据。

### 1.1 参考项目值得借鉴的 5 个设计

1. **机制写进数据，而不是写进 UI/渲染**：`bonds.json` 的 `bb`（数值）与 `spec`（tiers/formulas/caps/algorithm/assumed）把“阿戈尔战斗开始做什么”变成可读、可测的配置。
2. **排序是显式函数**：`egirOrder`/`egirReviveScan` 独立命名，注释写清“左/上/行 0 在底部”，避免散落在循环里。
3. **连链用队列 + 去重集合**：`seen`、`markedBy`、`layered` 三层保护，分别解决“自己/已标记/重复加层”，比递归或双重循环稳。
4. **生命周期钩子有优先级**：`battleStart`、`death` 的注册顺序/优先级明确（阿戈尔复活 11 先于不屈 10），边界行为可解释。
5. **测试直接写行为**：顺序、连链、同一目标多标记、复活槽位、护盾/防御、联防等都有 fixture，改坏了会立刻红。

> 本项目不需要照搬 1–5 的全部实现，但这 5 个“结构”值得在 P0/P1 中逐条落地。

## 3. 阿戈尔实现方案（推荐）

### 3.1 口径：先做“吞噬层数”，后做“生存与击倒”

**P0 只模拟“吞噬本身”会改变层数的部分：**

1. 战斗开始时，所有“已激活阿戈尔”的干员按“更靠左、再靠上”的顺序行动。
2. 每名阿戈尔标记“身前一格”的我方单位；若目标是阿戈尔，则继续标记该目标身前一格（连链）。
3. 每个“不同的被标记单位”每场战斗只加一次层数，数量 = 该单位等阶（I–VI → 1–6）。
4. 身前一格为空：不标记、不加层。
5. 目标不是阿戈尔：加层，但链在此终止。
6. 同一目标被多名阿戈尔标记：日志可显示多次标记，但层数只加一次。
7. 层数按“固定层”写入 `state.layers`（不是临时层），下一场战斗重新结算、可再次加。

**为什么可以先不做 5000 流失/退场：**

- 吞噬的“标记”在伤害结算前全部放置；层数只取决于“被标记的不同单位集合”。
- 一个单位被多名阿戈尔标记时，即使第一发 5000 流失把它击倒，它仍然已经“被吞噬”，仍然只加一次等阶层数；后续标记取消不会改变“它已被加过一次”的事实。
- 唯一例外是“战斗开始前就已经退场/倒下的单位”（参考项目的联防 `carry.down`）；本沙盒没有这个状态。
- 因此 **P0 的吞噬层数与完整模拟一致**；5000 流失只影响“目标是否退场/复活/克莱门莎加层”等 P1 内容。P0 **不包含**克莱门莎策略、未来幽灵鲨/归溟幽灵鲨等“被击倒加层”来源。

> 这条是本方案最重要的范围判断：不要因为“参考项目算了 HP”就以为层数也必须先有 HP。

### 3.2 数据：新增盟约机制文件

建议新增 `data/covenant_mechanics.json`，由 `tools/build_web_data.py` 读取并注入 `data.js` 的 `covenant.mechanics`。不要写进 `sandbox.js`（浊心斯卡蒂的硬编码就是前车之鉴）。

```json
{
  "version": 1,
  "source": "PRTS 卫戍协议·规程/PRTS盟约记录；本地 xlsx 交叉核对",
  "bonds": {
    "egirShip": {
      "mechanics": [
        {
          "type": "devour",
          "event": "onBattleStart",
          "order": ["colAsc", "rowAsc", "uidAsc"],
          "front": "facing",
          "chain": "throughMembers",
          "layers": { "per": "targetTier", "oncePerTargetPerBattle": true },
          "simulate": ["mark", "order", "chain", "layers"],
          "defer": ["damage", "death", "revive"],
          "damage": 5000,
          "damageType": "physicalHpLoss",
          "steal": ["baseAtk", "block"],
          "cancelOnTargetDown": true
        },
        {
          "type": "revive",
          "event": "onKnockdown",
          "requireEmpower": true,
          "charges": 3,
          "firstPerMember": true,
          "batchOrder": ["colAsc", "rowDesc", "uidAsc"],
          "defer": ["summon"]
        }
      ],
      "assumed": [
        "身前一格为空时不吞噬、不加层",
        "同一目标被多名阿戈尔标记时，层数只加一次",
        "本地坐标 r=0 为最上行；“靠上”= r 更小",
        "P0 不模拟 5000 物理流失与退场，吞噬目标视为存活"
      ]
    }
  }
}
```

构建校验建议：

- `bonds` 的 key 必须存在于盟约表；未知 key 直接失败。
- `type` 只允许白名单（`devour` / `revive` / ...）；`event` 只允许 `onBattleStart` / `onKnockdown`。
- `order` 只允许 `colAsc/rowAsc/uidAsc` 等枚举。
- `requireEmpower` 必须能从 `activation.empowerThreshold` 取到值；不要写死 5/6。
- `source`、`assumed` 必填，便于以后核对。

### 3.3 状态：每场一份盟约状态

```js
state.bonds = {
  egir: {
    started: false,          // 本场是否已结算战斗开始
    order: [],               // 发起吞噬的阿戈尔 uid（已排序）
    marks: [],               // { fromUid, toUid, tier }
    devoured: [],            // 被吞噬过的 uid（每场去重）
    layersGained: 0,
    revives: { charges: 0, used: [] }, // P1
    revivedOnce: {}          // P1：uid -> true
  }
};
```

重置点：

- `prepEnd` 进入作战期时重置。
- `battleEnd` 回休整期时重置。
- `battleStart` 重复触发不重置已结算状态（幂等）。
- 导入沙盒码时按快照恢复（P1 的 `GSPS2`）。

### 3.4 事件：先盟约，后干员

当前流程（`handleEvent('prepEnd')`）：

```text
phase = combat
battleCounters = {}
triggerEvent('onPrepEnd')
triggerEvent('onBattleStart')   // 只跑干员规则 + 授予特质
```

建议改为：

```text
phase = combat
resetBattleCounters()
resetBondBattleState()
triggerEvent('onPrepEnd')
beginBattle():
  1. runBondHooks('onBattleStart')   // 阿戈尔吞噬
  2. runOperatorHooks('onBattleStart')
  3. handleGrantFrontTrait()
  4. logBattleCapAuras()
battleStartDone = true
```

**报表时点**：当前 `prepEnd` 是在 `onBattleStart` 之后才 `generateReport('休整期')`，这样吞噬层数会被算进“休整期报表”。建议改成：

```text
triggerEvent('onPrepEnd')
generateReport('休整期')      // 只含休整期规则
beginBattle()                  // 吞噬层数留给作战期报表
```

如果希望立即看到吞噬结果，可另设一个不归档的“战斗开始”小计，或把 `beginBattle()` 的结果单独显示在阿戈尔面板；不要把吞噬混进“休整期”来源。

为什么“盟约先于干员”：

- 吞噬加的层数属于“战斗开始状态”；克莱门莎这类“战斗开始时按阿戈尔层数生效”的干员/效果应当能看到这些层数。
- 参考项目的 `battleStart` 钩子也是按安装顺序执行，盟约钩子先注册。
- 这是一个**假设**；如果官方/实测表明干员 `onBattleStart` 先于吞噬，只需调整 `beginBattle()` 内部顺序，并补一条测试。

幂等：

- `beginBattle()` 开头 `if (state.bonds.egir.started) return`。
- 手动 `battleStart` 事件若已结算，提示“本场战斗已结算战斗开始”，不再执行。
- 下一场 `battleEnd` 重置后才可再次结算。

### 3.5 算法：适配本沙盒坐标

**关键差异：参考项目行 0 是棋盘底部，“靠上”= 行号更大；本项目行 0 是界面顶部，“靠上”= 行号更小。** 不要直接复制 `b.tileR - a.tileR`。参考项目对 act1 数据还改用“从下到上、从左到右”的兜底顺序；本项目当前只支持「规程」，按左/上即可，不需要版本分支。

```js
// 本沙盒：c 小优先，其次 r 小（更靠上），最后 uid 稳定
function egirOrder(a, b) {
  return a.c - b.c || a.r - b.r || a.uid - b.uid;
}

function egirMembers() {
  const seenName = {};
  return state.board
    .filter(function (o) { return opTags(o).indexOf('阿戈尔') >= 0; })
    .filter(function (o) {
      // 与 Calc 的“不同干员”口径一致：同名重复只算一个发起者
      if (seenName[o.name]) return false;
      seenName[o.name] = true;
      return true;
    })
    .filter(function () { return isBondActive('阿戈尔'); })
    .slice()
    .sort(egirOrder);
}

// 纯函数：只生成计划，不改状态；休整期预览也用它
function planEgirDevour() {
  const members = egirMembers();
  const marks = [];
  const markedBy = {}; // markerUid -> [targetUid]

  members.forEach(function (m) {
    const mine = [];
    const seen = {};       // 本次标记已见过（含自己）
    const queue = [m];
    seen[m.uid] = true;

    while (queue.length) {
      const x = queue.shift();
      const t = frontOp(x, 1); // 按 x 的朝向取身前一格
      if (!t) continue;
      if (seen[t.uid]) continue;
      // 防止“目标已经标记过我”的环；参考项目也有同类保护
      if ((markedBy[t.uid] || []).indexOf(m.uid) >= 0) continue;

      seen[t.uid] = true;
      mine.push(t);
      marks.push({ from: m, to: t, tier: tierOf(t) });

      // 穿过被标记的阿戈尔继续连链
      if (opTags(t).indexOf('阿戈尔') >= 0) queue.push(t);
    }
    markedBy[m.uid] = mine.map(function (t) { return t.uid; });
  });

  return { members: members, marks: marks };
}

function applyEgirDevour() {
  const st = state.bonds.egir;
  if (st.started) return 0; // 幂等
  st.started = true;

  const plan = planEgirDevour();
  st.order = plan.members.map(function (m) { return m.uid; });
  st.marks = plan.marks;

  const done = {}; // 每目标每场只加一次
  let gains = 0;
  plan.marks.forEach(function (mk) {
    if (done[mk.to.uid]) return;
    done[mk.to.uid] = true;
    st.devoured.push(mk.to.uid);
    const label = mk.from.name + ' · 阿戈尔吞噬 → ' + mk.to.name +
      '（' + tierLabelOf(mk.to) + ' 阶）';
    gains += addLayer('阿戈尔', mk.tier, label, {
      opName: mk.from.name,
      targetName: mk.to.name,
      kind: 'bond:devour',
      detail: '吞噬',
      tier: mk.tier
    });
  });

  if (gains) log('阿戈尔：战斗开始吞噬 ' + st.devoured.length + ' 名，+ ' + gains + ' 层', 'event');
  else log('阿戈尔：战斗开始没有可吞噬的目标', 'warn');
  return gains;
}
```

边界：

| 场景 | 预期 |
|---|---|
| 身前一格为空 | 不标记、不加层、不报错 |
| 目标是阿戈尔 | 加层，并继续以该目标为起点连链 |
| 目标不是阿戈尔 | 加层，链终止 |
| 同一目标被 A、B 两名阿戈尔标记 | 标记两条，层数只加一次（`done`） |
| A→B→C 链 | B、C 各按等阶加一次；A 的标记集合包含 B、C |
| 目标已在本场被吞噬 | 跳过，不重复加层 |
| 阿戈尔未激活（<3 人） | 不结算，日志提示未激活 |
| 重复触发 `battleStart` | 不重复加层（`started`） |
| 下一场战斗 | 重置后可再次加层（层数累计） |
| 场上同名干员重复 | 先按名字去重（与 Calc 的“不同干员”口径一致）；若产品上允许重复，至少日志警告，避免同一目标被当成两个单位 |

`tierOf` 建议：

- 普通干员：`metaOf(name).tier`（1–6）。
- 自选干员：`OP_META` 里已按 6 阶处理，直接用；若未来有 `tier=0` 的数据，回退到 6 并在日志提示。
- 隐藏特殊干员：按数据表 `tier`，不要按稀有度。

### 3.6 示例：链式吞噬的层数

摆位（同一行，全部朝右；本地坐标 r=0 为最上行）：

```text
A(r4,c2,T6) → B(r4,c3,T3) → C(r4,c4,T1) → F(r4,c5,T6,非阿戈尔)
```

标记：

- A 标记 B、C、F（穿过 B、C 连链）
- B 标记 C、F
- C 标记 F

层数：

```text
B（III 阶）+3
C（I 阶）+1
F（VI 阶）+6
合计 +10
```

注意 F 被 A/B/C 三家标记，但只加一次 +6；日志可以写三条“标记”，报表只记一次层数。这个例子应作为 A8 的第一条测试。

### 3.7 复活与策略（P1）

**复活（阿戈尔强化）**

- 条件：`getEval()` 中阿戈尔 `row.state === 'empowered'`（本地数据是 6 人；不要写死 5；该状态已包含调和 +1 的口径）。
- 次数：`mechanics.revive.charges = 3`。
- 每名成员本场只可能消耗一次：`revivedOnce[uid]`。
- 战斗开始吞噬造成的击倒：先进入 `batch`，等所有吞噬结算完，再按 `c` 升序、`r` **降序**（本地 r=0 在顶部，先处理底部；参考项目 row0 在底部，其 `a.tileR - b.tileR` 等价于本地的 r 降序）消费复活次数。
- 战斗中后续击倒：立即消费剩余次数。
- 沙盒没有 HP/退场模型：P1 只做“标记已复活 + 日志 + 计数”，不真正把单位移出棋盘；在面板上明确写“沙盒不模拟退场/再部署时间”。
- 与不屈的优先级：参考项目是阿戈尔 11 > 不屈 10。本沙盒建议“阿戈尔复活成功则本次不再触发不屈”；若未成功，再触发不屈（若以后接入）。这是简化，需在 `assumed` 记录。

**克莱门莎策略（崇高牺牲）**

- 数据：`策略 / 克莱门莎 / 崇高牺牲`：“【阿戈尔】干员被击倒时，使已激活的【阿戈尔】盟约叠加等同于该干员等阶的层数”。
- 触发：`onKnockdown` 且被击倒者带阿戈尔标签、阿戈尔已激活。
- 加层：`addLayer('阿戈尔', tierOf(op), '克莱门莎 · 崇高牺牲', ...)`。
- 与复活独立：先加层，再判断复活；两者不互斥。

**歌蕾蒂娅策略（猎人战法）**

- 本地文本：“<在场6名不同【阿戈尔】干员> 效果替换为前3名【阿戈尔】干员首次被击倒时召唤整备区最右侧一名可部署至当前位置的【阿戈尔】干员”。
- P1 只做“开关 + 替换复活 + 提示召唤未模拟”；不要为了这条策略去实现整备区部署/召唤系统。
- 若开启，复活次数不再消费；日志写“歌蕾蒂娅：复活被替换为召唤，沙盒暂不模拟召唤”。

## 4. 现状证据（代码定位）

- **阿戈尔只有文本，没有机制**：`web/data/data.js` 的 `covenants` 中 `egirShip` 只有 `desc`、`valueText`、`activation`；`calc.js` 的 `judge()` 只按人数算激活/强化，不执行盟约效果（[calc.js](../web/js/calc.js#L249-L324)）。
- **规则引擎只遍历干员规则**：`applyRule()` 处理 `bonds/amount/perRound/perBattle/target` 等字段，没有“盟约在战斗开始时做什么”的分支（[sandbox.js](../web/js/sandbox.js#L1355-L1448)）。
- **战斗开始没有盟约钩子**：`triggerEvent('onBattleStart')` 只跑干员 `onBattleStart` + `handleGrantFrontTrait()`（[sandbox.js](../web/js/sandbox.js#L1568-L1609)）；`handleEvent('prepEnd')` 在进入作战期时调用它（[sandbox.js](../web/js/sandbox.js#L2204-L2214)）。
- **`isBondActive` 只查状态**：每次调用都会重算 `getEval()`，但没有“阿戈尔层数来源”的概念（[sandbox.js](../web/js/sandbox.js#L463-L474)）。
- **浊心斯卡蒂是硬编码**：`EXTRA_RULES['浊心斯卡蒂']` 只有文本，`handleDeployAuras()` 按名字 + `'阿戈尔'` 常量结算；修复报告也明确说这块“未改代码，只给思路”（[sandbox.js](../web/js/sandbox.js#L200-L206)、[sandbox.js](../web/js/sandbox.js#L1504-L1525)、[沙盒叠层修复报告.md](沙盒叠层修复报告.md#L105)）。
- **没有“被击倒”事件**：`EVENT_LABEL` 只有获得/刷新/休整/战斗/部署/技能/击倒敌人/售出/战斗中/被动，没有 `onKnockdown`；`归溟幽灵鲨`、`克莱门莎` 等只能显示“未模拟特殊效果”（[sandbox.js](../web/js/sandbox.js#L104-L117)、[sandbox.js](../web/js/sandbox.js#L2446-L2462)）。
- **“补满叠层”不含吞噬**：`applyBattleCaps()` 只补干员 `perRound/perBattle` 与已授予特质，不会补盟约级吞噬（[sandbox.js](../web/js/sandbox.js#L1615-L1673)）。
- **盟约弹层“当前数值”没有代入层数**：`bondPopHtml()` 直接 `nl2br(c.valueText)`，显示的是 `(35+1×层数)%` 原式（[sandbox.js](../web/js/sandbox.js#L2613-L2632)）。
- **测试覆盖不足**：`tools/test_sandbox.mjs` 共 42 项，阿戈尔只有一条“浊心斯卡蒂部署进范围”测试（[test_sandbox.mjs](../tools/test_sandbox.mjs#L582-L591)）。
- **规则数据不可重建**：`web/data/operator_rules.js` 第一行写“自动生成的干员规则”，但仓库里没有生成器；沙盒文件已从 `.git/info/exclude` 移出（2026-11-12），但生成器仍待补（[operator_rules.js](../web/data/operator_rules.js#L1-L2)、[沙盒叠层修复报告.md](沙盒叠层修复报告.md#L171)）。

**文本歧义**：本地 `desc` 是“（【阿戈尔】之间优先**对**更靠左和靠上的干员发起吞噬）”，参考项目/其 research 是“（【阿戈尔】之间优先更靠左和靠上的干员发起吞噬）”（无“对”）。两种读法：

- **读法 A（参考实现）**：更靠左/上的阿戈尔**先行动**（发起者顺序）。
- **读法 B**：阿戈尔优先**吞噬**更靠左/上的单位（目标优先级）。

两者会改变多阿戈尔相邻时的结果。建议 A7 先对照官方原文/实测；在结论出来前，按读法 A 实现，并在 `assumed` 里明确记录。

## 7. 不建议照搬的部分

1. **完整战斗模拟/服务端权威**：参考项目是完整游戏复刻；本项目是查询 + 配队 + 叠层沙盘，硬接战斗模拟会拖垮工期与包体。
2. **精确数值/名单**：3/5、9 人、幽灵鲨/斯卡蒂/归溟的旧 kit 都不能直接用于当前赛季。
3. **5000 物理流失 + DEF + 死亡/复活全链路**：需要全干员 HP/ATK/DEF/block 数据，当前 `data.js` 没有；不要为了“看起来完整”而编造数值。
4. **联防/镜像/队友吞噬**：参考项目为 1–4 人联机做了镜像与队友交互；本沙盒单棋盘，先不做。
5. **装备/铁镐/band/garrison 交互**：阿戈尔重刃、机变盟誓、整备区召唤等，等有对应系统再接。
6. **直接复制 `egirOrder`**：参考项目行 0 在底部，本地行 0 在顶部，比较函数方向相反；这是最容易抄错的一处。
7. **GPL 代码/测试/注释**：许可证不兼容；只按官方描述与行为独立实现。

### 8.3 术语

- **标记**：阿戈尔在战斗开始时选中“身前一格”的单位；一个标记对应一次 5000 物理流失（参考项目）。
- **连链**：被标记的目标如果也是阿戈尔，继续标记它身前一格。
- **层数**：本方案中每个“不同的被标记单位”每场加一次，数量为其等阶。
- **强化**：阿戈尔 6 人（本地数据）时的效果层；复活 3 次在此层生效。
- **固定层/临时层**：`state.layers` / `state.temp`；吞噬加的是固定层，下一场可再次加。
